# Coding agents converge on small, logged, replayable harnesses

As of October 2026, the verified evidence says a coding agent is a short loop over a typed, append-only event log, a small tool set (read, edit, search, bash), and a thin protocol boundary between the core and its clients. The best-documented event-sourced design is the OpenHands Software Agent SDK, Codex and ACP formalize the core-versus-client split, and the minimalist camp (mini-swe-agent, pi) shows that four tools and a linear history are enough to compete. The most useful quantitative result on context management is that simple observation masking matches LLM summarization on solve rate at roughly half the cost of raw history, while persistent memory, planning modes and multi-agent coding have no measured benefit in anything I could verify. The sharpest design risk sits in the provider layer: reasoning payloads (Anthropic signed thinking, OpenAI encrypted reasoning items, Gemini per-part thought signatures) cannot be translated across providers and must be stored opaque and tagged, and tool calls carry different ID schemes per provider. On evaluation, harness choice moves scores by 7 to 17 points on the same model according to secondary sources, repeat runs of one configuration spanned about nine points, and Terminal-Bench now exists in at least three versions, so every number needs a pinned dataset version, a pinned harness commit and at least five repeats. For the Python CLI, I would freeze the event schema, the neutral message model and the provider streaming interface early, and defer sub-agents, plan mode, semantic search and memory until an ablation justifies them. Several load-bearing questions remain unverified in any harness, notably how dangling tool calls are repaired on resume, and I list those explicitly below.

## Most numbers in this field are vendor claims or snapshots

The notes behind this report were gathered through page fetches that a small model summarized, so quoted wording should be spot-checked before it goes into a spec, and I grade every claim by where it came from. Tier A means a primary document or paper that the research read directly: arXiv papers, vendor API documentation, and source files such as Codex's `models.rs`. Tier B means a vendor reporting its own measurement on its own benchmark or internal eval, for example Anthropic's tool-search accuracy gains or Cursor's semantic-search results. Tier C means a secondary blog, aggregator, leaderboard mirror or search snippet that was never opened at the primary source. Most 2026 leaderboard numbers fall in Tier C, because the tbench.ai page I could reach showed Terminal-Bench 4.0 with an unpopulated table ([tbench.ai leaderboard](https://www.tbench.ai/leaderboard)), and several benchmark claims came only from search summaries.

Two further limits shape how much weight the evidence can bear. First, most primary edit-format and tool-ablation evidence is from 2024 to November 2025, and I found no 2026 independent edit-format benchmark; the newest Aider polyglot data is dated November 20, 2025 ([Aider leaderboard](https://aider.chat/docs/leaderboards/)). Second, no source I found measures the effect of persistent memory files, planning tools, repo maps or instruction files on task success. Where I make a recommendation in those areas, it is design judgment, and I mark it as such.

## The harness is a typed log, a loop and a thin client boundary

### Event-sourced state is documented in one place and approximated elsewhere

The OpenHands SDK paper is the only primary source that describes an event-sourced harness in detail. Every event is immutable with an ID, timestamp and source, serialized through discriminated unions. The model-visible layer holds `MessageEvent`, `ActionEvent` (tool calls) and observation events, while an internal layer holds `ConversationStateUpdateEvent`, `CondensationRequest`, `Condensation` and `PauseEvent` ([OpenHands SDK paper](https://arxiv.org/html/2511.03690v1)). `ConversationState` is the only mutable component, split into metadata and an append-only `EventLog`. Metadata is rewritten to `base_state.json`, each event is written as its own JSON file, and resume loads the metadata and replays the event directory. Condensation results are stored as events and applied before each LLM call, so the full history survives compaction ([OpenHands SDK paper](https://arxiv.org/html/2511.03690v1)). Tool dispatch validates the model's JSON arguments against a Pydantic `Action` model, runs a `ToolExecutor`, and converts the `Observation` back to LLM content, with tools referenced by registered name so specs stay serializable.

Other harnesses expose less. Claude Code resumes from `.jsonl` transcripts by session ID or by absolute path, and its headless `stream-json` mode emits newline-delimited typed messages: `system` (subtype `init`, with model, tools and a `capabilities` array), `assistant` and `user` with `parent_tool_use_id` for sub-agent nesting, optional `stream_event`, and a final `result` line ([Claude Code headless docs](https://code.claude.com/docs/en/headless)). Codex exposes `thread/start`, `thread/resume`, `thread/fork`, `thread/read` and `thread/items/list`, plus a `rollout/compress` method and a `ThreadRolledBack` event that old rollouts still replay ([codex-rs app-server README](https://github.com/openai/codex/tree/main/codex-rs/app-server)). Claude Code's internal transcript schema and Codex's rollout file format were not read, so I treat them as Tier C for design purposes. The minimalists use the simplest form: mini-swe-agent's trajectory and the message list sent to the model are the same object ([mini-swe-agent README](https://github.com/SWE-agent/mini-swe-agent)), and pi's loop runs until the model returns no tool calls, emitting events for everything to drive reactive UIs ([pi blog post](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)).

### Core as library is now the standard shape

Codex draws the line in its crate layout. The `codex-rs/protocol` crate defines types for communication between `codex-core` and `codex-tui` and separate types for `codex app-server`, and its README says it should carry minimal dependencies and no material business logic ([codex-rs protocol README](https://github.com/openai/codex/tree/main/codex-rs/protocol)). The app-server speaks request, response and notification messages over stdio, in-process and WebSocket transports ([codex-rs app-server README](https://github.com/openai/codex/tree/main/codex-rs/app-server)). ACP standardizes the same split for editors: JSON-RPC over stdio, the editor spawns the agent as a subprocess, one connection can host several sessions, `session/cancel` is a notification, and the agent can call back into the client for `session/request_permission`, file access and terminals ([ACP architecture](https://agentclientprotocol.com/overview/architecture), [ACP protocol overview](https://agentclientprotocol.com/protocol/overview)). Claude Code covers the scripting case with `claude -p`, `--output-format` of `text`, `json` or `stream-json`, and exit code 0 on success ([Claude Code headless docs](https://code.claude.com/docs/en/headless)). OpenHands splits `openhands.sdk`, `openhands.tools`, `openhands.workspace` and a REST and WebSocket `openhands.agent_server` ([OpenHands SDK paper](https://arxiv.org/html/2511.03690v1)). Language choice follows the ecosystem: OpenHands is Python with Pydantic, pi is TypeScript with TypeBox schemas, and Codex is a Rust workspace, with the Codex team's own rationale for Rust not retrieved. Nothing in the evidence argues against Python for a single-user CLI.

### Cancellation is documented well in one harness, and the key invariant is untested everywhere

Claude Code gives the most concrete semantics. SIGINT or SDK `interrupt()` ends the turn. SIGTERM exits with code 143, kills the process tree of any running Bash command, starts no new tool call or model request, records the running command as killed, and leaves the turn unfinished with no result. On resume the interrupted turn is left as is, and `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1` opts into continuing it ([Claude Code headless docs](https://code.claude.com/docs/en/headless)). The `system/init` event advertises capabilities such as `interrupt_receipt_v1` for feature detection. pi threads abort signals through the whole pipeline including tool calls, and aborted requests can return partial content with stop reason `aborted` ([pi blog post](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)). OpenHands `pause()` persists state and emits a `PauseEvent`, and `run()` resumes from the same point ([OpenHands SDK paper](https://arxiv.org/html/2511.03690v1)). What no source verifies is how any harness repairs a dangling `tool_use` or `function_call` on resume, even though both Anthropic and OpenAI require every tool call to have a matching result in the next request. That gap is the most consequential unknown for the cancellation design, and I treat the repair policy as something to design and test myself.

### Permissions are a pure check before dispatch

OpenHands pairs a `SecurityAnalyzer` that rates each call low, medium, high or unknown risk with a `ConfirmationPolicy` that can pause the agent in `WAITING_FOR_CONFIRMATION` and can change mid-session ([OpenHands SDK paper](https://arxiv.org/html/2511.03690v1)). Claude Code offers permission modes, rule strings such as `Bash(git diff *)`, and hooks that run even in headless mode unless `--bare` is set, which makes hooks a security boundary for CI use ([Claude Code headless docs](https://code.claude.com/docs/en/headless)). pi defaults to no permission prompts and recommends containers instead ([pi blog post](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)). These are all the same gate, a function of tool call, policy and mode, evaluated before dispatch.

## Tools: cheap guardrails survive while edit formats stay unsettled

### Edit formats have no winner, and error recovery matters more than syntax

Anthropic ships an exact-match tool (`str_replace_based_edit_tool`, type `text_editor_20250728`, with `view`, `str_replace`, `create` and `insert`), and OpenAI ships V4A `apply_patch` with `create_file`, `update_file` and `delete_file`, where the harness applies the diff and returns `Error: Invalid Context:` on a conflict ([Anthropic text editor docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/text-editor-tool), [OpenAI apply_patch guide](https://developers.openai.com/api/docs/guides/tools-apply-patch)). The Anthropic docs retrieved do not state what happens when `old_str` matches zero or several times, so that behavior needs a direct API test. Neither vendor says which models were trained on which format. Aider's polyglot leaderboard shows diff-style formats at the top (gpt-5 high at 88.0 percent with `diff`, 91.6 percent well-formed; Gemini 2.5 Pro at 83.1 percent with `diff-fenced`, 99.6 percent well-formed), while an older Aider table has a model at 100 percent compliance with whole-file output ([Aider leaderboard](https://aider.chat/docs/leaderboards/), [Aider edit leaderboard](https://aider.chat/docs/leaderboards/edit.html)). Aider publishes no causal claim linking format to pass rate, so the data measures format compliance, not edit success per call.

The best evidence on why recovery matters is SWE-agent's 2024 analysis with GPT-4 Turbo: **51.7 percent of trajectories contained at least one failed edit, and eventual edit success fell from 90.5 percent overall to 57.2 percent after a single failed edit** ([SWE-agent paper](https://arxiv.org/html/2405.15793v3)). Its ablations on SWE-bench Lite show the full interface at 18.0 percent resolved, versus 15.0 without the lint-on-edit check, 10.3 with no edit tool, 12.7 with a full-file viewer, and 11.0 for a shell-only baseline. Linting reverts a failing edit and returns the error with a before and after snippet, and search results are capped at 50 so the agent must narrow its query. These are 2024 results on an old model, so I read them as directional. The finding that has aged best is the guardrail: validate every edit, revert on failure, and cap search output. mini-swe-agent's self-reported score above 74 percent on SWE-bench Verified with bash alone ([mini-swe-agent README](https://github.com/SWE-agent/mini-swe-agent)) suggests strong current models need far less scaffolding, but that number names no model or date, so it is Tier C.

### Bash: process groups, sentinels and non-interactivity

Anthropic's reference bash tool keeps one long-lived shell with `exec 2>&1`, appends `echo __CLAUDE_BASH_DONE_<uuid>__` as an end sentinel, offers a `restart` flag, and starts the shell in its own process group so a timeout can kill all children ([Anthropic bash tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/bash-tool)). OpenAI's shell tool takes a `commands` array with per-command `timeout_ms`, echoes `max_output_length`, returns `{"type": "timeout"}` with partial output, and says execution should be non-interactive ([OpenAI shell tool guide](https://developers.openai.com/api/docs/guides/tools-shell)). mini-swe-agent runs each action as an independent `subprocess.run` and sandboxes by swapping in `docker exec`. Both vendor implementations kill the whole process group on timeout, and both push non-interactive commands. I found no primary source for output-truncation policy beyond OpenAI's `max_output_length`, or for Claude Code and Codex shell internals.

### Search, tool count and parallelism

Cursor reports that semantic search added an average 12.5 percent answer accuracy on its own Context Bench and 2.6 percent more code retention on codebases with over 1,000 files, and concludes grep plus semantic search is best ([Cursor semantic search blog](https://cursor.com/blog/semsearch)). That is a Tier B result on an unreleased benchmark with small online deltas, and the Morph figures (84.1 percent versus 64.2 percent) are Tier C. The Claude Code move from vector RAG to agentic search comes from a talk summary I did not verify. I would default to ripgrep plus glob. Anthropic's guidance is to start with a few consolidated tools, cap responses (25,000 tokens by default in Claude Code) and write actionable truncation messages ([Anthropic, writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)). Its deferred tool search reportedly cut a 58-tool MCP setup from about 55K to about 8.7K upfront tokens and lifted MCP eval accuracy from 49 to 74 percent on Opus 4, all from Anthropic's internal evals ([Anthropic, advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). The Anthropic API runs multiple tool calls from one turn concurrently by default, with `disable_parallel_tool_use` to turn that off ([Anthropic parallel tool use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)). Which tools a harness treats as concurrency-safe is not documented officially. Secondary write-ups describe reads in parallel and writes serial, and I adopt that as a sensible default without a primary source behind it.

## Masking beats summarizing on cost while memory has no measured payoff

### The one controlled compaction study favors the cheap option

The Complexity Trap paper from JetBrains Research and TUM compared raw history, observation masking (rolling window of 10 turns) and LLM summarization (21 turns summarized at a time, last 10 kept verbatim) in SWE-agent on 500 SWE-bench Verified instances with a 250-turn limit, across five model configurations ([Complexity Trap](https://arxiv.org/html/2508.21433v3)). Observation tokens make up about 84 percent of an average turn. On Qwen3-Coder 480B, raw history solved 53.4 percent at $1.29 per instance, masking solved 54.8 percent at $0.61, and summarization solved 53.8 percent at $0.64. On Gemini 2.5 Flash, masking cost 56 percent less and solved 35.6 percent versus 32.8 raw. The results are not uniform: on Gemini 2.5 Flash with thinking, raw solved 40.4 percent, masking 36.4 and summarization 31.4, and on Qwen3-32B both strategies lost a few points. Summary calls consumed up to 7.2 percent of total spend, and LLM-summary trajectories ran about 15 percent longer than raw on Qwen3-Coder. A hybrid gained 2.6 points over raw on a 50-instance subset. The paper treats SWE-agent as its main scaffold and OpenHands as initial evidence only, and several deltas sit within plausible noise, so "masking matches summarization" is the defensible reading and "masking wins" is not. I did not read the confidence intervals in Table 1.

Chroma's context-rot report tested 18 models and found performance declined with input length in every experiment, structured haystacks hurt, and needle position showed no notable effect, but it measures input-length probes rather than agent compaction, and Chroma sells a vector database ([Chroma](https://www.trychroma.com/research/context-rot)). ACE (arXiv 2510.04618) argues that rewriting summaries loses detail ("brevity bias" and "context collapse") and reports gains from incrementally updated playbooks, though I never saw its baselines ([ACE abstract](https://arxiv.org/abs/2510.04618)).

### Vendor compaction is server-side, and one version is opaque

Anthropic's compaction runs server-side in on-demand and token-threshold modes, with a custom summarization prompt option, a keep-recent-turns option, and a rule-based context editing feature that clears old tool results ([Anthropic compaction docs](https://platform.claude.com/docs/en/build-with-claude/compaction)). Its engineering post says to tune for recall first and precision second, and calls tool-result clearing one of the safest forms of compaction, with no benchmark numbers attached ([Anthropic, effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). The beta header names changed between versions (`compact-2026-09-04` in the current docs, an earlier `compact-2026-01-12` in a secondary snippet), so any code must check the live reference. OpenAI's `context_management` with `compact_threshold`, and the standalone `/responses/compact` endpoint, return an encrypted compaction item that the docs call opaque and advise not pruning ([OpenAI compaction guide](https://developers.openai.com/api/docs/guides/compaction)). That item is unauditable, so any debugging value must come from the application's own log. OpenHands' default is an LLM summarizing condenser that keeps the first N and last M events and records a `Condensation` event ([OpenHands condenser architecture](https://docs.openhands.dev/sdk/arch/condenser)). Its "up to 2x per-turn cost reduction" claim is a vendor blog figure I did not trace to a benchmark. Claude Code auto-compact internals and Codex's compaction were not found in any primary source.

### Caching constrains how history may be rewritten

Anthropic's cache checks a prefix in the order tools, system, messages, up to four breakpoints, and "changes at each level invalidate that level and all subsequent levels." Changing tool definitions invalidates everything, and changing the thinking parameters or `output_config.effort` invalidates message blocks ([Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). Cache reads cost 0.1x base input (0.05x on some newer models), cache writes 1.25x for five minutes and 2x for one hour. I did not verify how compaction or context editing interacts with the cache, but any rewrite of earlier messages must change the prefix from the edit point onward, so append-only histories keep cache hits and masking that edits old tool results gives them up. That is generic caching behavior and needs a test before the compaction design relies on it.

### Memory and repo context have no measured evidence

Anthropic describes structured note-taking, a NOTES.md-style file persisted outside the context window, and a client-side memory tool where the application executes view, create and edit operations under `/memories` ([Anthropic, effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [Claude memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). Aider's repo map sends a ranked symbol summary with a default budget of 1,000 tokens and lets the model request files ([Aider repo map](https://aider.chat/docs/repomap.html)). I found no solve-rate measurement for CLAUDE.md, AGENTS.md, memory files or repo maps, and the memory docs offer no validation or pruning of model-written notes. pi's author argues that tightly controlling what enters context beats added features ([pi blog post](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)), which is an opinion and not a measurement.

## Sub-agents help reading while verification is capped by the verifier

### Sub-agents work as context firewalls for read-heavy tasks

Claude Code sub-agents run in their own context window, start without the parent's history, and return only a final summary, with a default of 20 concurrent sub-agents and a nesting cap of 3 ([Claude Code sub-agents docs](https://code.claude.com/docs/en/sub-agents)). The docs recommend them for verbose output, tool restriction and self-contained work, and warn that many detailed returns can consume significant context. Anthropic's multi-agent research system reports a Claude Opus 4 lead with Sonnet 4 sub-agents beating single-agent Opus 4 by 90.2 percent on its internal research eval, at roughly 15x the tokens of chat, and says coding "has fewer parallelizable subtasks than research" ([Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). That is a Tier B result on research queries, so it does not transfer to coding. Cognition's "Don't Build Multi-Agents" argues for single-threaded agents because actions carry implicit decisions that conflicting parallel agents will violate, with illustrative examples and no benchmarks ([Cognition](https://cognition.com/blog/dont-build-multi-agents)). The two sources agree on the boundary: read-only sub-agents returning bounded summaries are fine, and parallel writers without a shared decision record are where things break. I found no controlled single versus multi-agent comparison on SWE-bench-style coding, and no measured benefit for plan mode or todo tools.

### Reproduction tests are hard, and red-to-green is a weak check

SWT-Bench converts SWE-bench into test generation and found that on the 276-instance Lite split the best configuration (SWE-Agent told to execute its own tests) reached only 18.5 percent success, versus 15.9 without execution and 3.6 for zero-shot ([SWT-Bench](https://arxiv.org/html/2406.12952v2)). Its failure catalog is useful for verifier design: tests that pass without reproducing the issue, loops after edits that fail to apply, environment setup failures, invalid test code, malformed diffs, and total failure on astropy, requests and flask. Newer systems report higher numbers (Issue2Test 32.9 percent on SWT-bench Lite, e-Otter++ 63 percent on a different benchmark), but those came from search snippets and use different benchmarks, so they are not comparable ([Issue2Test](https://arxiv.org/abs/2503.16320v3), [e-Otter++](https://arxiv.org/pdf/2508.06365v1)).

On selection across rollouts, snippet-level reports say each test-based verifier in R2E-Gym plateaus around 42 to 43 percent on SWE-bench Verified with 51 percent combined, and that SWE-ZERO/SWE-HERO's verifier-selected result trails Pass@K by about 15 percent at K=16 ([R2E-Gym](https://arxiv.org/pdf/2504.07164), [SWE-ZERO/SWE-HERO](https://arxiv.org/pdf/2604.01496)). I treat these as Tier C until opened, but the direction is consistent: verifier quality is the bottleneck, and a layered check (reproduction test, then regression suite, then a critic as tiebreaker) beats more rollouts. A fail-to-pass check accepts any failure, so a verify-first mode should require the failure to match the issue's symptom and fall back gracefully on repos where test generation fails outright. No production harness documents its done-detection or stuck-loop policy, so the turn cap, repeated-action detector and forced verification step I suggest later are my design judgment.

## Provider formats diverge exactly where reasoning and tool IDs live

### Reasoning payloads are opaque, signed or encrypted, and provider-scoped

Anthropic thinking blocks are `{"type": "thinking", "thinking": "...", "signature": "..."}`, and the docs require passing every block back "complete and unmodified" alongside the `tool_use` it accompanied, with modified blocks rejected with a 400 ([Anthropic thinking docs](https://platform.claude.com/docs/en/build-with-claude/thinking)). On current models thinking is on by default with `display` defaulting to `omitted`, which returns an empty `thinking` string with a real signature that is identical regardless of display setting. Manual `budget_tokens` thinking is rejected on Claude 4.7 and later in favor of adaptive thinking ([Anthropic extended thinking docs](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)). Forced `tool_choice` of `any` or `tool` returns a 400 on several current models, and forced tool use skips thinking ([Anthropic define tools docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). Streaming is a named-event SSE protocol (`message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop`) with `text_delta`, `input_json_delta`, `thinking_delta` and `signature_delta`, and the SDK accumulators reassemble blocks including signatures ([Anthropic streaming docs](https://platform.claude.com/docs/en/build-with-claude/streaming)).

OpenAI's Responses API is item-based: output is a list of typed items (`message`, `reasoning`, `function_call`, `custom_tool_call`) that are echoed back as input, reasoning items carry `encrypted_content` for stateless use, and the function-calling page says reasoning items returned with tool calls must be passed back with the outputs ([OpenAI reasoning guide](https://developers.openai.com/api/docs/guides/reasoning), [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)). Persisted reasoning is reusable only within a model family, and `reasoning.context: "all_turns"` is supported on the GPT-5.6 family and GPT-6.1 Sol. A load-bearing fact for any OpenAI adapter is that function calling on GPT-6 Astra and GPT-6.1 Sol requires the Responses API and is unsupported on Chat Completions ([OpenAI reasoning guide](https://developers.openai.com/api/docs/guides/reasoning)). Gemini's thought signatures are encrypted metadata attachable to any part, required for reasoning continuity in stateless mode ([Gemini thinking docs](https://ai.google.dev/gemini-api/docs/thinking)); the `generateContent` function-call and part-batching rules were not verified.

### Tool call IDs, usage and stop reasons need normalizing

Anthropic has one tool-call ID (`tool_use.id`). OpenAI function calls carry an item `id` (prefix `fc_`) and a `call_id` (prefix `call_`) that joins the output, and Codex's `FunctionCall` models the same pair with `call_id` required and `id` optional ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), [Codex models.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/models.rs)). Usage semantics differ too: Anthropic total input is `cache_read + cache_creation + input`, OpenAI bills the entire `previous_response_id` chain as input and counts reasoning in the max-token budget, and Gemini's `max_output_tokens` includes thought tokens ([Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [OpenAI conversation state](https://developers.openai.com/api/docs/guides/conversation-state)). OpenAI also warns that GPT-5.5 can treat an intermediate update as a final answer unless the assistant `phase` field is preserved on replay. pi-ai normalizes stop reasons to `pending`, `stop`, `length`, `toolUse`, `error` and `aborted`, and I verified no provider-native stop-reason enumeration beyond Anthropic's `end_turn` example.

### Existing abstraction layers confirm where abstractions break

pi-ai separates a provider (auth, catalog) from an API implementation (`anthropic-messages`, `openai-responses`, `openai-completions`, `google-generative-ai`), uses `text`, `thinking` and `toolCall` blocks, and streams events keyed by `contentIndex` with a partial snapshot that "shouldn't be retained as history" ([pi-ai README](https://github.com/badlogic/pi-mono/tree/main/packages/ai)). Its author reports that Anthropic's signed blobs add a transformation layer, that cross-provider handoff converts thinking into tagged text and is "inherently best-effort," that usage arrives at the start of the stream for some providers and the end for others, and that many unified APIs ignore abort and partial results ([pi blog post](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)). Codex's `ResponseItem` enum is internally tagged with an `Other` catch-all so unknown upstream item types still deserialize ([Codex models.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/models.rs)). LiteLLM maps one `reasoning_effort` knob onto different mechanisms by model generation, which is the same job a neutral effort table has to do ([LiteLLM Anthropic docs](https://docs.litellm.ai/docs/providers/anthropic)), though whether signatures and redacted blocks survive its OpenAI-shaped response was not verified. Gaps remain for Pydantic AI, the OpenAI Agents SDK, Vercel's reasoning part shape, Azure AI Foundry and retry and backoff behavior.

## Benchmark numbers need pinned versions and five repeats

### Terminal-Bench has several versions and Harbor is the runner

The Terminal-Bench paper is arXiv 2601.11868 and appeared at ICLR 2026 ([ICLR 2026 proceedings](https://proceedings.iclr.cc/paper_files/paper/2026/hash/444a3737adaee10d86ad2ef5f74468e6-Abstract-Conference.html)). The tbench.ai pages I fetched headline Terminal-Bench 4.0, a June 2026 blog refers to 2.1, and `terminal-bench@2.0` still exists as a dataset, so the version must be written into every run ([tbench.ai leaderboard](https://www.tbench.ai/leaderboard)). The 89-task count and per-task Docker containers come from a secondary page. Harbor, the runner, is described as a framework for running any agent with any model on any task in any sandbox in parallel, installed with `uv tool install harbor` ([Harbor GitHub](https://github.com/laude-institute/harbor)). A custom agent is a Python class selected with `-a module:Class`: `BaseInstalledAgent` (preferred; Harbor installs the CLI inside the task container, with `name()`, `install()` and `run()`) or `BaseAgent` (the loop stays outside the container and acts through `environment.exec(...)`) ([Harbor custom agents](https://docs.harborframework.com/agents/custom-agents.md)). Useful run flags include `-d` for dataset with `@version`, `-k` for attempts, `-n` for concurrency, `-e` for sandbox, and `--print-config`, and a job config is saved to `config.json` ([Harbor run a job](https://docs.harborframework.com/jobs/run-a-job.md)). The terminal-bench repo says to run the oracle agent first to confirm all tasks work and itself uses `@latest`, which drifts ([terminal-bench repo](https://github.com/harbor-framework/terminal-bench)). Not read: the ATIF trajectory spec, pinning semantics, per-command timeouts, tmux behavior, and Windows or WSL support.

### Harness effects and run variance exceed many leaderboard gaps

All Terminal-Bench 2.0 leaderboard figures I have are Tier C. Third-party snapshots put the top at 80 to 83 percent with GPT-5.5 near the top ([Codesota](https://www.codesota.com/benchmark/terminal-bench-2)), and a Snorkel analysis reportedly found a median of 28.2 percent across 142 submissions with the top 10 within about 7 points ([Snorkel](https://www.snorkel.ai/blog/terminal-bench-2-0/)). A secondary blog reports Claude Opus 4.6 at 58.0 percent in Claude Code versus 74.7 percent in Terminus-KIRA, a 16.7-point harness effect ([harness performance blog](https://codex.danielvaughan.com/2026/04/09/harness-performance-terminal-bench/)). The strongest primary-ish variance evidence is the LemonHarness technical report: five jobs of one submission spanned **80.90 to 89.89 percent, mean 84.49, across 445 trials** ([LemonHarness](https://arxiv.org/pdf/2606.24311)). That is a self-reported, non-peer-reviewed report, but it matches the 89-task by five-attempt arithmetic and implies that single-run harness comparisons are weak evidence.

### SWE-bench Pro replaces Verified as the public reference

Scale's SWE-bench Pro has a 731-instance public set, an 858-instance held-out set kept off the public board, and a 276-instance private set, 1,865 tasks across 41 repositories in total. Public rows carry confidence intervals of about 3 to 3.6 points, top rows use mini-swe-agent, and some rows used a 50-turn cost-capped setting while others used 250 turns ([Scale SWE-bench Pro public](https://labs.scale.com/leaderboard/swe_bench_pro_public)). Rankings are defined by non-overlapping confidence intervals, and the page is undated. The claim that OpenAI stopped reporting SWE-bench Verified over contamination comes from a URL I saw but never fetched, with a date conflict between September 2025 and February 2026, so I keep it at Tier C. Dollar cost, wall-clock time and Docker requirements for a full run were not found in any primary source.

## Decisions for the Python CLI

The table maps each foundational decision to its evidence and confidence. Confidence reflects the evidence tier, and "design judgment" marks recommendations the evidence supports only indirectly.

| Decision | Recommendation | Main evidence | Confidence |
|---|---|---|---|
| Session log | Append-only JSONL, Pydantic discriminated-union events with ID, timestamp, source, an `Other` catch-all, two layers (model-visible and internal), resume by replay, fork by prefix copy | OpenHands SDK, Codex `models.rs`, Claude Code resume | High on shape, medium on JSONL versus per-event files |
| Message model | Item-based, not message-based. Reasoning as `{provider, model_family, kind, payload verbatim, display text}`. Tool calls with internal ID, provider call ID and optional item ID. Parallel calls as a list | Anthropic signatures, OpenAI reasoning items, Gemini signatures, Codex enum | High |
| Streaming interface | Async iterator of typed events with partial snapshots, core consumes only finished blocks, abort in the signature, official SDKs under the adapter | pi-ai, Anthropic SDK accumulators | Medium to high |
| Core as library | One event union, typed Python API, `--json` JSONL on stdout with an init event, `result` last, defined exit codes. ACP only if editor integration is a goal | Codex protocol crate, Claude Code headless, ACP | High |
| Cancellation | Cancel is a logged state transition. Kill the process group. Synthesize a result for dangling tool calls. Resume leaves the interrupted turn unless opted in | Claude Code docs, pi, OpenHands | Medium, repair step unverified |
| Tool set | Windowed read with line numbers, exact-match edit with zero and multi-match errors, write, grep, glob, bash. Validate and revert edits. Cap outputs | SWE-agent, Anthropic and OpenAI tool docs | Medium |
| Compaction | Masking first, summarization as a measured ablation, results stored as events | Complexity Trap, OpenHands | Medium |
| Evaluation | Harbor integration, pinned dataset and harness commit, oracle run, five or more repeats, Terminus 2 baseline | Harbor docs, LemonHarness | Medium |

### Log, message model and provider interface come first

The log is the foundation because everything else reads it. I would write one Pydantic discriminated union covering user messages, assistant items, tool calls, tool results, reasoning items, compaction events, cancellation events and usage events, with IDs and a monotonically increasing sequence number, and a catch-all `Other` variant so schema evolution does not break old sessions, as Codex does. Per-event files (OpenHands) and JSONL (Claude Code, and what pi's "cleanly documented session format" goal implies) are both append-friendly. JSONL is the simpler option for a solo build, and I would pick it. Store raw provider payloads next to the neutral form so an adapter bug can be replayed offline. The neutral message model should be item-based because both Codex's production enum and OpenAI's wire format treat reasoning and tool calls as first-class items. Reasoning must be stored verbatim and tagged by provider and model family, replayed only to the same family, and degraded to tagged text on handoff, with the UI saying so. Usage needs separate fields for new input, cache read, cache write, output and reasoning, with the raw provider usage kept alongside, because the providers count differently. Effort and thinking settings belong in one adapter table keyed by model, since manual thinking budgets are rejected on newer Anthropic models and OpenAI rejects `none` or `minimal` effort on some GPT-6 models.

The streaming interface should yield events tagged by block index with a partial snapshot for the UI, while the core appends only finished blocks to the log. Take the signature accumulation from the official SDK helpers, since signature handling is the part most likely to break, and keep SDK types behind the adapter boundary. Put the abort token and the "partial message with aborted stop reason" state in the interface from day one.

### Cancellation, tools and compaction are decisions I can make with evidence, and the rest I should measure

For cancellation, adopt Claude Code's contract (interrupt ends the turn, terminate kills the process tree, resume leaves the turn alone unless opted in) and add what no source documents: on resume, synthesize an explicit "interrupted, not executed or outcome unknown" result for every tool call without a result, log it as an event, and write a test against both APIs' ordering invariants. That is my inference, since no harness's repair behavior was verified. For tools, start with read, edit, write, grep, glob and bash, which matches the minimalist consensus and Anthropic's guidance on few consolidated tools. Run bash as a fresh subprocess in its own process group with stdin closed and a hard output cap by default, and add a persistent session only when a workflow needs it. Mark read-only tools concurrency-safe, serialize everything else, and let one failed write not cancel independent reads. Add an OpenAI `apply_patch` adapter only if per-model tuning shows a gain, because the evidence says format preference varies by model family.

For compaction, the evidence supports building the measurement before the policy. Log per-turn token counts split into observation, reasoning and user content (observations were 84 percent of turns in the one study), record each compaction as a log event, and run masking, summarization and the hybrid as variants with the model, scaffold and dataset fixed, reporting solve rate, cost per instance, turn count and summary-call cost share with repeats. Because rewriting history breaks the cache from the edit point onward, test cache-read fractions as well. Treat sub-agents, plan mode, memory files and semantic search as out of the first release: the sources give no measured coding benefit for any of them, and the cost multipliers (about 15x tokens for multi-agent research) are documented.

### Eval integration should be designed in, not bolted on

Implement a Harbor `BaseAgent` first, because the loop then stays on the host and can reach any model endpoint while acting inside the task container through `environment.exec`, though that fit is my inference from the docs and `BaseInstalledAgent` with `--allow-agent-host` may be needed if the agent must live in the container. Read the ATIF spec before freezing the event schema, since trajectories and usage data are parsed in `populate_context_post_run` and an ATIF exporter may be cheaper to build in from the start than to retrofit. Run the oracle agent, then Terminus 2 on the same model and budget as the neutral baseline, record dataset version, Harbor version, harness commit, reasoning effort, turn and cost limits and attempts with every number, and report the mean with min and max across at least five jobs. I would smoke-test a single task on this Windows machine through Docker Desktop with WSL2 before planning a full run, because Harbor's Windows support is undocumented, and use a cloud sandbox (Modal or Daytona, both named in the Harbor README) for any real sweep.

## Conclusion

The pattern across these sources is that the parts of a coding agent with the strongest evidence are the unglamorous ones: an immutable log, a validated and bounded tool interface, provider payloads stored verbatim, and measurement discipline. The parts attracting the most attention (sub-agents, planning modes, memory, semantic search, elaborate summarizers) have the least measured support, and the one controlled compaction study found the cheapest strategy as good as the expensive one in most configurations. That reorders the build: the log, the neutral model and the eval harness are the foundation, and features earn their way in through ablations the eval harness already supports.

The unresolved questions are concrete enough to test in the first weeks. Does the chosen provider endpoint round-trip encrypted reasoning and output items? What exact behavior does Anthropic's `str_replace` have on zero and multiple matches? Which dangling-tool-call repair does each API accept on resume? How do compaction and masking affect cache reads? What does the ATIF schema require? What do Windows and WSL do under Harbor? Until those are answered and the Terminal-Bench version is pinned, I would not publish a score, because with a nine-point spread between repeats of one configuration, a single number says little about the agent.
