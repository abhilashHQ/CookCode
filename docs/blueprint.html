1 · The map

Three layers, and the core never touches the outside world directly

The core is a Python library. It runs the loop, builds what the model sees, and gates tool calls. Everything it talks to sits behind one of three interfaces: a Provider (the model), an Environment (the machine tools run on), and the Session log (where every event lands). Clients on top only consume events and send input back. The CLI, the TUI, headless mode and the Harbor benchmark adapter are all clients of the same library.

2 · One turn

What happens between your prompt and the answer

The loop is short. It builds a request from the log, streams the model's reply, appends the finished items, runs any tool calls through the gate and the environment, appends the results, and repeats until the model stops calling tools. Partial text goes to the client for display but never into the log. Only finished items get written.

    T->>E: exec / read / write

    T-->>L: results
    L->>G: append results
  end
  L-->>U: result event
3 · The log

The session is an append-only log, and everything else is a view of it

This is the decision the rest depends on. Every event gets written once to a JSONL file with a sequence number and is never edited. What the model sees is computed from the log each turn. That one rule gives us five features for the price of one:

flowchart LR
  LOG[("Session log
append-only JSONL")]
  LOG --> MC["Model context
full · masked · summarized"]
  LOG --> UI["Client stream
CLI, TUI, headless"]
  LOG --> RES["Resume and fork
replay a prefix"]
  LOG --> TR["Eval traces
export per run"]
  LOG --> CK["Flagship 2
checkpoints"]

Model-visible events

User message, assistant message, reasoning, tool call, tool result. These are what the context builder turns into a request.

Internal events

Approval asked and answered, compaction marker, interruption, repair, usage, errors. The model never sees these, but replay, evals and the UI all do.

  • Compaction becomes a different view of the same log. Turning it on or off replays an identical session, which is how we get honest ablation numbers.
  • Each event keeps the raw provider payload next to our neutral form, so an adapter bug can be replayed offline without paying for another call.
  • There's an Other catch-all event type so old sessions still load after the schema changes. Codex does the same thing.
  • The closest published design is the OpenHands Software Agent SDK. It's the main reference for this layer.
4 · Items

Our own message model, built from items

Providers disagree on shape, so the core speaks its own format and adapters translate at the edge. The research changed the unit from "messages with content blocks" to a flat list of items, because that's how Codex and OpenAI's Responses API represent reasoning and tool calls, and it fits Anthropic's blocks without loss.

ItemWhat it holdsWhy it's shaped this way
messageRole plus text (and later images)The plain case every provider agrees on.
reasoningProvider, model family, opaque payload stored verbatim, optional readable summaryAnthropic signs it and OpenAI encrypts it. It can only go back to the same model family. Switching models degrades it to labeled text.
tool_callOur ID, the provider's call ID, optional provider item ID, tool name, JSON argumentsOpenAI uses two IDs (id and call_id), Anthropic one. Parallel calls are just several items in a row.
tool_resultThe call ID it answers, output, status (ok, error, interrupted)Both APIs reject a tool call with no matching result, so the status field is what makes cancellation repair possible.

Usage gets its own record split into new input, cache read, cache write, output and reasoning, plus the raw provider numbers, because each provider counts differently.

5 · Environment

Tools never touch the OS directly

This one is new since the first plan. Every tool goes through an Environment interface with three operations: run a command, read a file, write a file. The point is that the same tools then work in three places without a rewrite:

flowchart LR
  T["read · edit · write
grep · glob · bash"] --> ENV["Environment
exec / read / write"]
  ENV --> L["Local
your repo, WSL2"]
  ENV --> H["Harbor container
Terminal-Bench tasks"]
  ENV --> S["Flagship 2 sandbox
later"]

Harbor's documented way to plug in a custom agent with its own loop is BaseAgent. The loop runs on the host and acts on the task container through environment.exec(...). Our Environment interface lines up with that one-to-one. Flagship 2 then supplies a sandboxed Environment, and the agent doesn't change.

This also sets the platform. Benchmark tasks are Linux containers, killing a command's whole process tree is a POSIX thing, and Harbor doesn't document Windows support. So the target is Linux, and you'd develop in WSL2.

6 · Cancellation

Ctrl-C at any point leaves a log we can resume

Interrupting is a logged state change. If you interrupt during a tool run, we kill the process group. Every tool call passes through three logged states: the model asked for it, we started it (written to disk before the command runs), and it finished. On resume, the repair pass gives each call left without a result a synthetic one, based on how far it got:

Last logged stateTool kindSynthetic result
Asked for, never startedanyinterrupted: not executed, safe to re-issue
Started, never finishedread-onlyinterrupted: outcome unknown, safe to retry
Started, never finishedmutatingunknown: may have run, inspect before retrying. Never re-run automatically.

Durable runtimes like DBOS and Cloudflare Workflows simply re-run the step that was cut off, and Inngest's docs admit a side effect can commit before its result is saved. None of the agents we checked document an "outcome unknown" state. This is what lets Flagship 2 kill a worker mid-run without running a command twice, and it's the part to explain in interviews.

stateDiagram-v2
  [*] --> Idle
  Idle --> Streaming: prompt
  Streaming --> Tools: tool calls
  Tools --> Streaming: results appended
  Streaming --> Idle: no tool calls
  Streaming --> Interrupted: Ctrl-C
  Tools --> Interrupted: Ctrl-C, kill process group
  Interrupted --> Repaired: synthetic results for dangling calls
  Repaired --> Idle
7 · Context management

Masking first, summarizing as an experiment, and measuring everything

There's one controlled study that compares these, the Complexity Trap paper (SWE-agent, 500 SWE-bench Verified tasks). Masking old tool outputs matched LLM summarization on solve rate at about half the cost of keeping raw history. Qwen3-Coder 480B: raw 53.4% at $1.29 per task, masking 54.8% at $0.61, summary 53.8% at $0.64. On one thinking model both methods hurt (40.4% raw, 36.4% masking, 31.4% summary). So there's no free lunch here, and we have to measure it ourselves.

What we build

  • A token ledger per turn, split into tool output, reasoning and user text
  • Masking of old tool outputs, written to the log as an event
  • Summarization and a hybrid as switchable variants

What we measure

  • Solve rate, cost per task, turn count
  • Cache-read share. Rewriting old history breaks the prompt cache from that point on, so masking in batches might keep most of the savings. Nobody has published that number yet.

10 · Stages

Four stages, each with its own architecture and its own locks

The order follows dependencies. Context engineering can't be measured until a real agent runs and an eval suite exists, and memory can't be judged until context engineering has a baseline. Each stage has decisions locked before it starts and decisions made at its end gate, using what the stage taught us. Thick borders mark what's new in that stage. Dashed borders mark harnesses that test the system without being part of it.

11 · Memory

Supermemory-style, adapted to code

Supermemory stores atomic facts in a temporal graph. A new fact can update an old one (the old one is kept for history but marked not-latest), extend it, or be derived from several. A background "dreaming" pass consolidates raw input into facts, episodes decay, preferences strengthen, and a small profile gives always-on context. It's built for remembering people across conversations.

My take: use it for cross-session repo memory, and keep it out of in-session context management. Two reasons:

  • Inside one session, about 84% of tokens are tool output. Fact extraction does nothing for that. Masking does.
  • Injecting retrieved memories into every request changes the prompt prefix each turn and breaks the cache. Memory enters as a fixed profile at session start, plus a recall tool.

The adaptation that makes it interesting for code: repo facts go stale when the code changes, which a chat memory never has to deal with. So every fact carries provenance (file paths, commit, content hash). A changed file marks its facts stale, the same way Supermemory's updates relation marks old facts not-latest.

The interview angle: "how do you keep agent memory from lying after a refactor?" No source we found measures memory's effect on coding tasks, so this gets an ablation (no memory, AGENTS.md-style notes, fact memory) and we publish whatever comes out, including zero.

13 · Unknowns

Things we test early instead of assuming

  • Which dangling-tool-call repair each provider API actually accepts on resume (M1, then M3)
  • What Anthropic's exact-match edit does on zero or multiple matches, if we copy its format (M2)
  • Whether the chosen provider endpoint returns reasoning payloads we can replay unchanged (M3)
  • What Harbor's trajectory format (ATIF) requires, before the event schema freezes (M4)
  • Whether Harbor runs cleanly under WSL2 with Docker Desktop (M4 smoke test)
  • How much masking and summarization cost us in cache reads (M7)
