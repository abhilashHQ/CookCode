## 2. The parts worth reading closely

### `gate.py:_plan_bash`
An allowlist over the lexer's output, not a pattern match on the string. A command passes only if it is analyzable, not opaque, writes to no file, sets no variable, and every command in it, including those inside process substitutions, names a program on `_PLAN_FORBIDDEN` with none of that program's forbidden flags. A denial names the offending part, so the model can route around it.

### `gate.py:mode_at`
The mode at the end of a log: the latest `mode_changed`, `run_started` or `session_started`. The loop uses it in `_build` to decide whether `exit_plan`'s schema goes out, so the tool list stays a pure function of the log, like `loaded_tools` (0048).

### `loop.py:_gate_exit_plan`
`exit_plan` never reaches `decide`. Outside plan mode it is an error result. In plan mode the approver sees the plan, and the answer maps to ask, auto-edit or feedback. On approval it appends `approval_resolved`, then `mode_changed`, then sets `self._mode`, so the next call in the same batch is gated in the new mode.

### `loop.py:_prologue`
Compares the mode the log ends in with the mode this run starts in. If plan mode is entered or left, it appends `mode_changed(source="run")` after `run_started` and the repairs, and before the prompt. The builder renders it as a user note, so the model is told in the same position on replay.

### `render.py:Printer`
Consumes stream events and log events, like `Display`. Finished things are printed once: an assistant message when its item is logged, a tool block when its result arrives, the plan panel when `exit_plan` is called. Everything still changing (the streaming text, calls in flight, usage, the last context estimate) is kept in `LiveState` for the live region to draw.

### `inline.py:InlineApp`
A non-full-screen prompt_toolkit application run under `patch_stdout(raw=True)`, so `Printer`'s writes land above the live region. `InlineApprover.decide` sets a `Menu` and awaits its future; a "no" sets `feedback` and awaits the next Enter in the input box. A run is an asyncio task; Esc and Ctrl-C cancel its token, and a second Ctrl-C cancels the task.

## 3. The life of a planned change

1. `cookcode --mode plan --once "check.py fails. Find out why and fix it."`
2. `_prologue` logs `run_started` (mode plan) and `mode_changed(plan, previous=None, source="run")`. The first request carries `PLAN_NOTE` before the prompt and `exit_plan` among the tools.
3. The model runs `ls -la` and reads files. `decide` allows `ls` through `_plan_bash` with rule `mode:plan`.
4. It tries `python check.py`. `_plan_bash` returns "python is not on the read-only list", and the result says to call `exit_plan`.
5. It calls `exit_plan(plan=...)`. `_gate_exit_plan` asks, and the user answers `a`. The log gets `approval_resolved(allow, "plan approved into auto-edit mode")` and `mode_changed(auto-edit, previous=plan, source="exit_plan")`. The tool result says the mode is now auto-edit.
6. The next request has no `exit_plan` schema. The model edits `dates.py`, which auto-edit allows inside the workspace. `check.py` passes.

## Cross-questions

1. **Why enforce plan mode in the gate instead of the prompt?** A prompt is a request and a gate is a guarantee. The claim "nothing changes state while planning" is only defensible if code refuses the call.

2. **Why not drop the mutating tools from the request?** Changing the tool list breaks the prompt cache, and the model would lose bash for reading. Keeping the schemas and denying with a reason costs one wasted call at most, and the reason teaches the model the rule.

3. **Then why is `exit_plan`'s schema filtered?** It is one tool, and sending it to every session would change every request ever recorded. It is filtered by `mode_at(events)`, so the request stays a pure function of the log.

4. **Why an allowlist for bash rather than a denylist?** A denylist has to anticipate every way to write a file. An allowlist only has to know what each listed program can do, and anything new is refused by default.

5. **What does the allowlist still trust?** That listed programs do not write through means outside their flags. Repository config that makes `git diff` run an external program is outside the threat model, and `--ext-diff` itself is refused.

6. **Why are user allow rules ignored in plan mode?** A standing `edit:*` rule says "don't ask me about edits", not "edit while planning". Deny rules still apply first, so planning can only be stricter.

7. **Why does approval map to ask or auto-edit, not back to the previous mode?** A session can start in plan mode with no previous mode, and the user should decide how much to trust the plan at the moment they read it.

8. **Why is the exit_plan mode change not a note in the context?** It happens between a tool call and its result. A user message there makes an invalid request for OpenAI-style APIs. The tool result says the same thing in a valid position.

9. **How does replay handle a mode change?** Notes come from `mode_changed` events and the tool list from `mode_at`, both functions of the log. `cookcode replay` rebuilds the same items.

10. **What happens in headless plan mode?** `PolicyOnlyApprover` denies `exit_plan`, so the run ends with the plan in the transcript. That is a plan-only run, which is what a non-interactive plan should be.

11. **Why drop the full-screen TUI the day it was built?** It kept the transcript in a widget. Scrollback, search and copy stopped working, and no styling could change where the transcript lived. Printing finished output into scrollback and redrawing only a small live region fixes the cause.

12. **How do printed history and the live region avoid tearing?** All output goes through `patch_stdout(raw=True)`. Each write erases the live region, prints, and redraws it, inside the application's event loop.

13. **Why do pipes keep the old line client?** A pipe has no terminal to draw a live region on, and scripts want plain lines. `run_cli` picks the inline client only when stdin and stdout are TTYs.

14. **How was the look verified?** In a real terminal, not only in tests. A terminal emulator library showed leftover live regions because it never answers cursor-position requests; under tmux, which does, the output was clean.

15. **What was the stdin crash?** `connect_read_pipe` gives stdin to a transport that closes it at EOF. `Terminal.close` then called `fileno()` on a closed file. With the descriptor gone there is nothing to restore, so `close` now checks `closed` first.
