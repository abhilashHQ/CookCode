# M3 walkthrough and cross-questions

This document describes M3 as the code exists on branch `dev`, on top of M0 to M2. Read it with `docs/decisions/0021` to `0027` open. M2 is in `docs/walkthroughs/m2.md`. Where a sentence names a function or file, it exists.

## 1. Map and dependency rule

M3 adds one package and three modules:

- `providers/openai_compat.py`: adapter A. `to_messages` and `build_body` (request side, pure), `SSEDecoder`, `ChatStreamAssembler` (response side, pure), `OpenAICompatProvider` (HTTP, retries, cancellation).
- `providers/cassette.py`: `Cassette`, `RecordingTransport`, `ReplayTransport`, `first_difference`.
- `agent/instructions.py`: `load_instructions` and `render_system`.
- `cli/`: `terminal.py` (terminal I/O, `Display`, the `DisplayProvider` and `ObservedLog` wrappers, `TerminalApprover`) and `app.py` (argument parsing, wiring, the REPL, Ctrl-C). The console script is `harness`.

Core changes are additive (0020): `ToolCall.raw_arguments`, the stream event `StreamRetry`, and the log event `provider_retry`. The loop changed in two places: `_stream` logs `StreamRetry` as `ProviderRetry`, and `_resolve` answers a call with `raw_arguments` with an error result.

Dependency rule: `agent/` still imports only core, its own modules and the protocols. `instructions.py` reads files through the `Environment`. The CLI is a client and may import anything. The new runtime dependency is `httpx`, used by the adapter and cassettes only.

## 2. File by file

### `providers/openai_compat.py`
Request side. `to_messages(request, provider=...)` groups each run of assistant-side items into one assistant message, keys results by `provider_call_id`, prefixes non-`ok` results with `[status]`, replays reasoning only to the same provider and model, sends `raw_arguments` verbatim, and raises on a result without its call (0023). `build_body` adds `stream: true`, `stream_options.include_usage`, the tools, `max_tokens` and any `extra_body`.

Response side. `SSEDecoder.feed(line)` returns a `data` payload when an event completes. Comments are skipped and multi-line data is joined. `ChatStreamAssembler.feed(chunk)` returns display events (`ItemStarted`, `ItemDelta`) and accumulates reasoning details by `index`, text, and tool-call fragments by wire index. An error object in a chunk raises `StreamFailure`. `finish()` raises a retryable `StreamFailure` when there is no `finish_reason`. Otherwise it returns every `ItemDone` in first-seen order, then `UsageReport`, then `StreamEnd`. Usage splits cached and cache-write tokens out of `prompt_tokens`. `output` is `completion_tokens` as billed, and `reasoning` is the reported subset.

`OpenAICompatProvider.stream` opens a client, then loops over attempts. Each attempt runs `_pump` as a task that does the HTTP and pushes events into a queue. `_attempt` races the queue against the cancel token, and its `finally` cancels the pump, which closes the connection. `stream` iterates the attempt under `contextlib.aclosing`, so leaving early (success, failure or abort) closes it at once instead of at garbage collection. A test caught exactly that leak. Between attempts it yields `StreamRetry` and sleeps on the cancel token (0022).

Invariants: no `ItemDone` before `finish_reason`. Every exit path yields exactly one `StreamEnd`. A cancelled token makes no request.

### `providers/cassette.py`
Recording tees the response stream, so streaming still works while recording. Replay compares the request JSON exactly and reports the first differing path. Request headers are never recorded (0024).

### `agent/instructions.py`
Root files first, then the launch directory's, deduplicated by content hash, each capped at 32,000 bytes (0025).

### `cli/terminal.py`
`Terminal` reads lines through `connect_read_pipe`, so a pending read can be cancelled by Ctrl-C. When stdin is not a pipe or TTY it falls back to a thread. It restores the blocking flag on close. `Display` renders stream deltas (reasoning dimmed) and log events: calls with a diff for `edit` and a preview for `write`, results with a preview, retries, errors, interrupts, budgets, undo and the final status. `DisplayProvider` and `ObservedLog` feed it through `_Observer`, which disables a failing sink instead of letting it raise into the loop (0026). `TerminalApprover` asks yes, no, or always. The always rule is narrow: `bash:<exact command>`, or `<tool>:<path>` for a single-path call. The loop's `_narrow` still checks it with `covers`.

### `cli/app.py`
`Session` finds the workspace (git top level, else the launch directory), opens a new session log under `$HARNESS_HOME` (default `~/.local/share/harness`), creates the checkpoint store, loads instructions, and builds the `Agent`. Ctrl-C works in three steps: during a run, the first press cancels the run's token (a cooperative interrupt, logged as `interrupted`). A second press cancels the run task (a hard stop that the next run's repair pass cleans up). At the prompt, a press exits. `--once` runs one prompt and exits with the headless exit codes (0 done, 1 error, 2 budget, 130 interrupted). `/undo [n]` calls `undo`. `run_cli(args, provider=...)` accepts any `Provider`, which is how the CLI tests run end to end on `FakeProvider`.

## 3. The life of a request over OpenRouter

Setup: a new session, mode `yolo`, the user asks the model to read a file.

1. `_prologue` appends `session_started`, `run_started` and `user_message`. `_step` builds the request and appends `model_request_started(r1)`.
2. `stream` posts the body. The first attempt gets HTTP 429 with `Retry-After: 2`. `_http_failure` reads the error body and returns a retryable `StreamFailure`. `stream` yields `StreamRetry(attempt=1, delay_s=2.0, status=429)`, and the loop appends `provider_retry(r1, 1, 2.0, "HTTP 429: ...", 429)`. The CLI prints `[retry 1]`.
3. The second attempt streams reasoning deltas (dimmed on screen) and the fragments of one tool call. None of it is in the log yet.
4. `finish_reason: "tool_calls"` arrives, then a usage chunk, then `[DONE]`. `finish()` yields `ItemDone(Reasoning)`, `ItemDone(ToolCall)`, `UsageReport` and `StreamEnd(tool_use)`. The loop appends two `item` events and `model_request_finished(r1)`.
5. The tool runs as in M2. The next request's `to_messages` produces one assistant message with `content: null`, the call and the `reasoning_details`, then the `tool` message keyed by the provider's call id.

If the stream had been cut after step 3, step 2 would repeat with `attempt=2`, and the log would still contain one copy of the response.

## 4. What the probes and cassettes established

Against OpenRouter on 2026-10-26 (spec section 15 open questions):
- **Repaired results.** A request whose tool call has no result is rejected with HTTP 400 (`TOOL_CALLS_MISSING_RESULTS`). An `interrupted` result written as text is accepted. The repair pass is what makes a resumed session sendable.
- **Order.** Results in swapped order and a user message between a call and its result were accepted by the Cohere and Nvidia backends. That is lenient, and not something to rely on.
- **Reasoning round trip.** Both backends accepted their own `reasoning_details` back on the next turn. That is now a recorded, replayed fact, not an assumption.
- **Free tier.** Of seven tool-capable free models, two worked. 0027 records the rest.

## Cross-questions

1. **Why not use the OpenAI SDK?** The adapter's job is the wire mapping, retries with a visible log entry, and cancellation semantics. The SDK owns all three and hides two. OpenRouter's reasoning fields are off-schema anyway. Answer: 0021.

2. **What happens if the connection drops halfway through a response?** Nothing reaches the log until `finish_reason`, so the adapter retries the whole request, logs `provider_retry`, and the log ends up with one copy. The cost is the tokens spent on the failed attempt. Answer: 0022.

3. **Why not emit a tool call as soon as its arguments are complete?** Because then a later failure in the same response cannot be retried without duplicating that call in the log. Tools run after the response anyway, so emitting early gains nothing.

4. **How is a retry different from the M1 crash repair?** Repair handles tool calls whose execution state is unknown, and never re-executes mutating ones. A model request has no side effects outside the log, so re-sending it is always safe as long as the failed attempt left nothing in the log.

5. **The model sent invalid JSON for a tool call. What does it see?** An error result saying the arguments are not a JSON object, quoting the start of what it sent, and its own raw text in the replayed assistant message. Without `raw_arguments` it would see a misleading "field required". Answer: 0023.

6. **Why put the status in the text of a tool result?** Chat Completions has no error flag on `tool` messages. Without the prefix, `denied` and `unknown` would read like successful output.

7. **How do you know a recorded cassette still matches the code?** Replay compares every request body to the recorded one and fails on the first differing JSON path. A change to the request mapping cannot pass silently. Answer: 0024.

8. **Why record at the HTTP layer instead of the Provider interface?** The SSE decoder, the assembler and the request mapping are the code most likely to break, and recording above them would skip all three.

9. **How does the CLI show streaming text when the core never prints?** It wraps the Provider and the SessionLog with decorators that pass everything through and call a sink. The core is unchanged. A failing sink is disabled rather than allowed to raise into `append`. Answer: 0026.

10. **Why read AGENTS.md once per run instead of following `cd`?** Prompt-cache prefix stability, and `system_prompt_sha256` on `run_started` then describes exactly what the model saw. Answer: 0025.

11. **What does Ctrl-C do mid-stream?** The first press cancels the run's token. The adapter's queue race sees it, cancels the pump task (closing the connection) and yields `StreamEnd(aborted)`. The loop logs `interrupted(streaming)`. The test sends a real SIGINT and checks exit code 130.

12. **Reasoning from model A, session continued on model B?** `replayable_to` fails because the family is the model id, so A's reasoning is not sent. Text and tool history carry over. Logging the drop is M5.

13. **What did the probes show about providers and repaired histories?** A missing result is a 400. Order and an interleaved user message were tolerated by two backends. The repair invariant (every call has a result before the next request) is what matters, and order is kept anyway.

14. **Why does `Usage.output` include reasoning tokens?** It is what is billed (`completion_tokens`). One backend reported more reasoning tokens than completion tokens, so subtracting would go negative. Budgets count input plus output, as in 0012.

## Known gaps in M3

- Real-task acceptance runs are pending (section 5).
- Tokens from failed attempts are not counted (0022).
- No connection reuse across turns (0021).
- The plain CLI has no steering input. Typing during a run is not read until the prompt returns. Steering is supported by the core and lands with the TUI or headless stdin.
- Raw request and response payloads are not stored by reference yet (`model_request_finished.raw_ref` stays empty). The recording transport is the mechanism if this is wanted.
