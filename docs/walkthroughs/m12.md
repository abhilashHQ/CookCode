# M12 walkthrough and cross-questions

This document describes M12 as the code exists on branch `m12-providers`. Read it with `docs/decisions/0054` open. Where a sentence names a function or file, it exists.

## 1. Map

- `providers/catalog.py` (new): `Preset`, `PRESETS`, `CLOUD_PRESETS`, `WindowProbe`, `is_local_url`, `needs_key`.
- `providers/discovery.py` (new): `Discovery`, `discover`, and the probes in `_window`.
- `core/strategy.py`: `DEFAULT_TRIGGER`, `Strategy.for_window`.
- `core/events.py`: `ContextSource`, `RunConfig.context_window`, `RunConfig.context_source`.
- `agent/loop.py`: `AgentConfig.context_window` and `context_source`, copied into the run config by `_run_config`.
- `config.py`: `Settings.context_window`.
- `cli/app.py`: `make_provider` reads the preset's protocol and read timeout; `api_key`, `missing_key`, `resolve_window`, `prepare_endpoint`, `window_notice`; the `--context-window` flag. `run_cli` calls `prepare_endpoint` after the key check.
- `cli/headless.py`: the same key check and `prepare_endpoint` call.
- `cli/inline.py`: `context_meter` and the `context.full` style.
- `evals/`, `harbor/agent.py`: read presets from the catalog and stay on the cloud presets.

## 2. The parts worth reading closely

### `discovery.py:discover`
At most two GETs, one client, a 3 s timeout. The first, `{base}/models`, lists the served models. When the preset has a probe, a second request (or the same listing, for OpenRouter and vLLM) gives the window. `_get` turns every failure (connection, HTTP status, non-JSON, a URL httpx refuses) into `_Unavailable`, and `discover` turns that into `Discovery.problem`. Nothing escapes, because a startup probe must never be the reason the agent fails to start.

### `discovery.py:_window`
One `match` arm per probe, each reading exactly one field. The docstring and the test `test_trained_maximum_is_never_used` carry the rule: the number the server loaded, never the number the model was trained for.

### `cli/app.py:prepare_endpoint`
Runs once per client start, after `load_resumed` and the key check. It asks the server only when there is something to learn: a probe exists, or no model was named. Tests that inject a provider get no network unless they also pass a discovery transport. Then it picks the model, resolves the window by `resolve_window`, and replaces `args.strategy` with `args.strategy.for_window(window)`, so the resolved trigger is what `RunConfig.strategy` records.

### `strategy.py:Strategy.for_window`
`model_fields_set` says whether the user wrote `t`. If they did, or the strategy never summarizes, nothing changes. Otherwise `model_copy` sets the trigger and marks it as set, so a second call is a no-op.

## 3. The life of a local run

1. `llama-server --jinja -c 16384 -m qwen2.5-coder-7b-q4.gguf` is running on port 8080.
2. `uv run cookcode --provider llamacpp --strategy hybrid`.
3. `apply_provider` sets the base URL to `http://localhost:8080/v1`, `api_key_env` to `None` and `model` to `None`. `missing_key` returns `None`.
4. `prepare_endpoint` calls `discover`. `GET /v1/models` lists one model and `GET /props` gives `n_ctx` 16384. The model is that one id, the window is 16384 from `server`, and the strategy becomes `hybrid:k6:b8:t8192`.
5. `run_started` records `context_window=16384`, `context_source="server"` and that strategy.
6. The usage line reads `ctx ~1.9k / 16k`. When the estimate passes 8192, `_summarize_if_needed` writes `compaction_applied` and the next request carries the summary.

## Cross-questions

1. **Why not read `n_ctx_train`, or LM Studio's `max_context_length`?** They are what the model was trained for, not what the server loaded. llama.cpp started with `-c 4096` on a 128k model reports both, and sizing by the larger one sets a 64k trigger on a 4k context, which overflows on every long run.

2. **Why doesn't replay need the window?** The window only decides when a summary is made. The summary itself is logged in `compaction_applied`, and the builder is a pure function of the log, so a replayed request is identical whatever window the replaying machine resolves.

3. **Then why record it at all?** Provenance. When a run summarized early or overflowed, the log says which window it believed and where that number came from.

4. **Why cap the derived trigger at 48k?** Every measured result from M6 on used 48k. Without the cap, a 128k cloud window would move the trigger to 64k and silently change the baseline the ablations compare against.

5. **Why half the window and not 90%?** The estimate is characters over four, and code runs closer to three characters per token, so the real prompt is larger than the estimate. The reply also needs room in the same window.

6. **What happens with Ollama when the user forgets `OLLAMA_CONTEXT_LENGTH`?** Ollama loads 4096 tokens and exposes no way to ask how much it loaded. CookCode assumes the preset's 4096, prints the small-window notice under a non-summarizing strategy, and summarizes at 2048 under `hybrid`. The preset note tells the user how to raise it. If they raise it on the server and not with `--context-window`, CookCode summarizes earlier than it needs to, which wastes a little and breaks nothing.

7. **Why does discovery never raise?** It runs before anything else, against servers that are often not started yet. A failure there must leave the user with a clear message or a fallback, never a traceback, and a model that was named explicitly should still run.

8. **Why is a low default safer than a high one?** Too low: summaries come early and cost a side call. Too high: the server truncates or rejects the prompt, and with Ollama the model answers a question it never fully saw.

9. **Why only seven presets when Sutra ships 24?** Each preset is a claim that the endpoint works. The four local ones are the reason for M12, and the other cloud entries are one line each when one is actually used.

10. **Why do tests that inject a provider skip discovery?** Every existing client test injects a fake provider and must stay offline. Discovery runs only when no provider is injected, or a test passes a discovery transport on purpose.

11. **What still isn't verified?** Every probe against a running server, and vLLM's `max_model_len` field, which only third-party code documents. 0054 says so until a live run is recorded.
