This document describes M9 as the code exists on branch `dev`. Read it with `docs/decisions/0044` to `0046` open, and 0041 for the hook mechanism. Where a sentence names a function or file, it exists.

- `subagents.py`: `task_tool`, `Spawner`, `missing_sections`, `_report_check`, `SECTIONS`, `REPORT_CHARS`, `CHILD_MAX_TURNS`.
- `skills.py`: `parse_skill`, `load_skills`, `skills_profile`, `skill_tool`.

## 2. The parts worth reading closely

### `subagents.py:task_tool`
It builds a child `Agent` from the `Spawner`: the same provider, model, store, mode, policy, approver and checkpoints, and the parent's tools minus `task`. The system prompt is the parent's plus `CHILD_PROMPT`, which describes the report. The child runs with `CHILD_MAX_TURNS` and the `report` stop hook. Its final text is capped at 8000 chars, and a footer naming the child session is appended.

### `_report_check`
A stop hook. `missing_sections` looks for the four Markdown headings. While any is missing, the child is sent back with the list. After `max_stop_blocks` the report goes back as it is, so a weak child degrades instead of hanging.

### `skills.py:parse_skill`
`FRONTMATTER` splits SKILL.md into frontmatter and body. `name` must match `^[a-z0-9][a-z0-9-]{0,63}$` and `description` must be non-empty, or the skill is ignored. `load_skills` merges the user's skills with the repository's, and the repository's win.

### `userhooks.py:_run`
The payload is base64-encoded into the command line and decoded into the hook's stdin, so no quoting can break it. It goes through `env.exec` at the repository root with the hook's timeout. Only exit 2 blocks.

## 3. The life of a delegated investigation

1. The parent, on `investigate-*`, calls `task(prompt="Find every place that retries HTTP calls and report the policy each uses.")`.
2. `task` is mutating, so it runs alone. A child session starts in the same store.
3. The child greps and reads 30 files in its own context. The parent's context grows by nothing during that time.
4. The child tries to finish without an Evidence section. The `report` hook blocks: "missing sections: Evidence". The child adds file and line references and finishes.
5. The parent receives the report (at most 8000 chars) with a footer naming the child session. Its next request carries the report and nothing the child read.
6. `cookcode stats` on the run directory counts both sessions. The ablation compares parent input tokens and total tokens against `ctx-raw`.

## 5. Gate decisions (owner, 2026-10-27)

- Return contract: a structured report.
- Child tools: the parent's full tools, sequential.
- Skills: SKILL.md folders.
- Hook API: shell commands with JSON on stdin.

## Cross-questions

1. **Why a structured report rather than free text?** The parent sees nothing but the report. Fixed sections force the child to separate what it concluded from what it saw and what it doesn't know. Without the Evidence section, a parent cannot tell a finding from a guess.

2. **Why enforce sections with a hook instead of asking in the prompt?** The same reason as verify-first: prompts get skipped. The hook already existed, and the contract cost about 20 lines.

3. **Why give the child full tools?** Read-only children cannot do delegated edits such as "update every call site". The owner chose full tools with sequential runs, so children never race on the same files.

4. **Why no recursion?** A child that can spawn children makes cost and depth unbounded. One level covers the use cases.

5. **Why does the child share the parent's approver?** Delegation must never widen permissions. In ask mode, the user is asked about the child's mutating calls exactly as about the parent's.

6. **How does a child survive a crash?** It doesn't resume on its own. The parent's `task` call is mutating and started, so on resume it is `unknown` (0011) and the model decides what to do. The child's partial log is still in the store.

7. **When does delegation cost more than it saves?** When the child reads little. The parent then pays for a child prompt, the child's requests and the report, on top of what it would have spent itself. The ablation reports parent tokens and total tokens separately for that reason.

8. **Why list skills at session start instead of searching for them?** A handful of one-line descriptions costs less than a search call, and a fixed listing keeps the prefix cacheable. Search is the move when skills number in the dozens, as with MCP tools in 0048.

9. **Why does the repository win on a skill name clash?** The repository's procedure is the one its maintainers review. A user's personal skill should not silently override a team's.

10. **Why shell commands for hooks instead of Python plugins?** Any language works, a crash cannot take the session down, and the contract is three exit codes and one JSON object.

11. **Why do broken hooks fail open?** A typo in a hook would otherwise wedge every session in the repository. Hooks are for workflow checks. Security boundaries belong in the policy, which fails closed.

12. **Why are hooks off unless the feature is on?** A repository's settings can declare hook commands. Cloning a repository and running the agent must not execute them silently.

13. **Why base64 the payload?** Tool arguments contain quotes, newlines and shell metacharacters. Encoding means no input can change the command that runs.

14. **How do user hooks show up in replay?** As `hook_blocked` events, the same as built-in hooks. Replay renders the logged message and never reruns the command.
