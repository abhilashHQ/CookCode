# M7 walkthrough and cross-questions

This document describes M7 as the code exists on branch `dev`. Read it with `docs/decisions/0038` and `0039` open. Where a sentence names a function or file, it exists.

## 1. Map

- `core/strategy.py`: `Strategy` (raw, mask, mask_batched, summarize, hybrid; k, b, t), `parse`, `label`. It is recorded in `RunConfig`.
- `agent/context.py`: `mask_cutoff`, `placeholder`, `_mask`, `_apply_summary`, `latest_summary`, `summary_cut`, `transcript`, `token_ledger`, `shared_prefix_tokens`, and `SIDE_VIEWS`, which the builder skips.
- `agent/loop.py`: `_summarize_if_needed`, `_side_call`, and the ledger on `model_request_started`.
- `core/events.py`: `CompactionApplied` (strategy, range, tokens before and after, summary text) and `ModelRequestStarted.ledger`.
- `tools/recall.py`: `recall(call_id)` reads a masked output back from the log.
- `evals/context.py`: `session_cost`, `render`. Backs `cookcode eval context`.
- `evals/stats.py`: `calibration` (reported input / chars-over-4 estimate).

## 2. The parts worth reading closely

### `context.py:mask_cutoff`
`cutoff = made - k`, and with batching, rounded down to a multiple of b. Between jumps the masked set stays the same, so consecutive requests share their prefix and the provider's cache serves it. Plain masking moves the cutoff every step, which rewrites one early result per request and invalidates everything after it.

### `context.py:_mask`
It masks results of steps below the cutoff that are longer than 200 chars and whose call is still in view. The placeholder states the size and the tool and how to get it back: `recall(call_id="...")`. The original never leaves the log.

### `loop.py:_summarize_if_needed`
It runs before a step when the built request would pass `trigger_tokens`. `summary_cut` picks the range from just after the first user message to just before the last k steps. The summarizer is a side call (view `summarize`), logged but skipped by the builder. Its text goes into `CompactionApplied` with `tokens_after` measured by building a probe request. A failed or empty summary is simply not applied.

### `evals/context.py:session_cost`
It walks a session's agent requests in order and rebuilds each under the target strategy from the events up to that point. It sums the estimated input, and for each request counts the part shared with the previous one (plus the system prompt and tools) as cacheable.

## 3. The life of a masked output

1. Step 3: `bash("pytest -q")` returns 9 KB of output. It is logged as a `ToolResult`.
2. Steps 4 to 9 run normally. Under `mask_batched:k6:b8`, the cutoff is `(made - 6) // 8 * 8`, which stays 0 until 14 requests have been made.
3. At request 14 the cutoff jumps to 8. Steps 0 to 7 with outputs over 200 chars are replaced by placeholders. That request misses the cache once; the next 7 share its prefix.
4. The model needs the test output again and calls `recall(call_id="call_3")`. The tool scans the log and returns the original.
5. `cookcode replay` rebuilds every request from the log plus the recorded strategy. The `items_sha256` values match.

## 4. Acceptance

- `tests/test_compaction.py`: masking past k steps, short outputs left alone, batched jumps keeping the prefix, logged summaries applied only under summarizing strategies, the cut keeping the task and the last steps, the ledger split, the shared-prefix count, recall, masking refused without recall, and the counterfactual on one trajectory.
- Counterfactual on 24 suite sessions (196 requests): `mask:k6` -4.2% input, `mask:k3` -9.8%, `mask_batched` -0.3%. Uncached tokens double under plain masking.
- Counterfactual on 50 Terminal-Bench sessions (794 requests): `mask:k6` -39.7%, `mask:k3` -47.9%, `mask_batched:k6:b8` -29.6%. Uncached: 1.32M raw, 4.41M `mask:k6`, 1.89M `mask_batched`.
- Calibration: x1.07.
- Live comparison (raw, `mask_batched:k6:b8`, `hybrid:k6:b8:t48000` on the 24 base tasks) in 0036.

## Cross-questions

1. **Why does plain masking cost more than raw on a caching provider?** Each step rewrites one early tool result into a placeholder, so the cached prefix ends there and everything after it is billed uncached. On Terminal-Bench, uncached tokens went from 1.32M to 4.41M while total input fell 40%. With cache reads at a tenth of the price, the net is worse.

2. **What does batching buy exactly?** The cutoff moves every b steps, so b-1 of every b requests keep the previous prefix. It keeps most of the saving (30% on Terminal-Bench) at a fraction of the cache loss, and it is the only strategy that beat raw on effective cost.

3. **Why do summaries live in the log instead of being recomputed?** A summary is a model output and not reproducible. Logging it in `compaction_applied` keeps the builder a pure function of the log, so replay never calls a model and rebuilt requests match.

4. **Why are summaries cumulative from the first user message?** Two overlapping summaries would duplicate or contradict content. Each new summary covers everything from the start up to a later point and replaces the previous one.

5. **What happens if the summarizer fails?** Nothing is applied and the run continues raw. A failed compaction never breaks a session, it just leaves it bigger.

6. **Why is recall needed?** Masking without it loses information. With it, a wrong masking decision costs one tool call. It also gives a signal: recall rates show whether k is too small.

7. **Why does the counterfactual skip summarize and hybrid?** They need a model call to produce the summary. The counterfactual's value is that it costs nothing and is exact for what the log can rebuild alone.

8. **What can the counterfactual not tell you?** How the model behaves with masked history: extra recalls, re-reading files, worse decisions. The trajectory is fixed, so the saving is an upper bound. Live runs measure the rest.

9. **How accurate is chars/4?** Reported input over the estimate came to 1.07 on 50 sessions. Good enough to rank categories and strategies. It would not be good enough for billing.

10. **Why log the ledger on every request rather than compute it later?** Later code might build requests differently. The log records what was actually sent, by category, at the time.

11. **Why did masking barely help on the local suite?** Suite sessions average 8 requests. With k=6 almost nothing is old enough to mask. The strategy pays off on long sessions, which is why the decision cites both measurements.

12. **Where is the token trigger measured?** On the built request's estimate (`estimate_tokens`), before each step. It sits at 48,000, well under the window, so a summary happens before a context error, not after.

13. **Why are side calls skipped by the builder and replay?** They are not part of the conversation. The summarizer's request and reply would otherwise show up as turns, and replay would expect them in the conversation's tape.

14. **What is the default, and why?** Raw. It is the measured baseline, and the numbers show masking is a window tool more than a cost tool on a caching provider.
