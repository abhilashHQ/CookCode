# M4 walkthrough and cross-questions

This document describes M4 as the code exists on branch `dev`, on top of M0 to M3. Read it with `docs/decisions/0028` to `0031` open. M3 is in `docs/walkthroughs/m3.md`. Where a sentence names a function or file, it exists.

## 1. Map and dependency rule

M4 adds:

- `cli/headless.py`: `run_headless`, `StdinApprover`, `LineReader`, `final_text`.
- `cli/commands.py`: `harness schema` and `harness export`.
- `cli/observe.py`: `ObservedLog`, `DisplayProvider` and `_Observer`, moved out of `terminal.py` so the headless client does not import terminal code.
- `cli/app.py`: `Runtime` (workspace, store, environment, agent factory) shared by the plain and headless clients. `load_policy` reads policy files.
- `export/atif.py`: `to_atif`, the log-to-ATIF projection.
- `env/harbor.py`: `HarborEnvironment` over a structural `Container` protocol.
- `harbor/agent.py`: `HarnessAgent`, the Harbor `BaseAgent` subclass.
- `core/events.py:event_schema` and `env/base.py:render_capped` (extracted from the local environment so both environments truncate identically).

There are no core behavior changes. Dependency rule: only `harbor/agent.py` imports `harbor`, and it is installed as the optional extra `harness[harbor]` (also a dev dependency, for tests). `env/harbor.py` and `export/atif.py` know harbor's shapes but not its classes.

## 2. File by file

### `cli/headless.py`
`run_headless(args, provider=, stdin=, stdout=)` checks the key and policy (errors go to stderr), builds a `Runtime` whose log sink writes `event.model_dump_json()` lines when `--json` is set, and picks the approver: `StdinApprover` for `--approvals stdin`, otherwise `PolicyOnlyApprover` (an open approval is denied). SIGINT and SIGTERM cancel the run token, and a second signal cancels the task. The exit code comes from `EXIT_CODES`. In text mode it prints `final_text`, the last assistant message of the last run.

`StdinApprover.decide` reads one line and parses it as `ApprovalAnswer` (`extra="forbid"`). A wrong `call_id`, invalid JSON or EOF each return a deny with a reason the log keeps. `LineReader` reads on a daemon thread and posts lines with `call_soon_threadsafe`. EOF is sticky. A pending read never blocks interpreter exit, unlike `asyncio.to_thread`, which the default executor would wait on.

### `cli/commands.py`
`main` dispatches a first argument of `schema` or `export` before parsing the agent's arguments. `export` reads a session from `$HARNESS_HOME`, runs `to_atif`, and writes to stdout or `-o`.

### `export/atif.py`
`_Builder.add` walks the events once. User and steer messages become user steps, each `model_request_started` opens an agent step, and items fill it in. `ToolResult` goes to the step recorded in `call_steps` for its call. `model_request_finished` sets metrics. Interrupts, budgets and errors become system steps. `trajectory()` numbers the steps, drops `None` fields, and refuses an empty log, because ATIF needs at least one step (0029).

### `env/harbor.py`
`_wrap` builds the per-call script and `_kill_script` builds the killer (0030). `exec` races the container exec against cancel and timeout. On either it kills the group, waits up to 10 s for the first exec to return its partial output, then cancels it. `_parse` finds the header line and decodes up to two base64 lines. `read_file` maps exit codes 2 and 21 to `FileNotFoundError` and `IsADirectoryError`, the same exceptions the file tools already handle from the local environment. `write_file` resolves the real path, creates the parents, uploads next to the target, copies mode and owner, and renames.

### `harbor/agent.py`
`split_model` reads the preset prefix. `run` asks the container for `pwd` (the task's workdir), builds `HarborEnvironment`, opens a session log in `logs_dir/sessions`, loads `AGENTS.md` from the container, and runs the loop in `yolo` mode. `report` (in `finally`) fills `AgentContext` and writes `trajectory.json`.

## 3. The life of a Terminal-Bench trial

`harbor run -p <tasks> -i fix-git -a harness.harbor.agent:HarnessAgent -m nim/minimaxai/minimax-m3.1-flash`

1. Harbor builds and starts the task container, constructs `HarnessAgent(logs_dir=..., model_name=...)`, calls `setup` (nothing to install), then `run(instruction, environment, context)`.
2. `run` gets `/app` (or wherever the task's workdir is) from `pwd`. The loop starts as in M3, and the model calls `bash`.
3. The bash tool wraps its command (cwd tracking, M2). `HarborEnvironment.exec` wraps it again: setsid, pidfile, output to `/tmp/harness-exec-<id>/out`. It sends one `docker compose exec` and gets back `HARNESS-EXEC <code> <size>` plus base64.
4. The run ends with `end_turn`. `report` writes `trajectory.json` and the token counts. Harbor runs the verifier and records reward 1.0.

If Harbor's agent timeout fires, it cancels `run`. The `finally` still exports whatever the log holds, and any started tool group is killed only if the cancel reached `exec`. A hard Harbor cancel during a tool leaves that process to die with the container.

## 4. Acceptance status

- Oracle run passes: `fix-git`, reward 1.0, 33 s.
- One real task end to end in WSL2: our agent on `fix-git` with NIM MiniMax M3.1 Flash, reward 1.0, 16 steps, 442 s (435 s of it model latency, 7 s of tools), four 429s retried. The trajectory validates as ATIF v1.8 (0031).

## 5. Tests

`test_headless.py` (verbatim stream, text mode, stdin answers and their failures, policy files, SIGINT and SIGTERM, schema drift), `test_atif.py` (validated against harbor's `Trajectory`: round trip, denied call, repaired and interrupted logs, orphan result, export command), `test_harbor_env.py` (a fake container whose timeout kills only the client, like docker: byte-identical output to the local environment, group kill on timeout and cancel, leftover children, files past the argv limit, symlinks, modes) and `test_harbor_agent.py` (the adapter end to end on the fake container). 896 tests in total.

## 6. Gate decisions (owner, 2026-10-26)

- **Schema version policy (0028).** Version is `SCHEMA_VERSION`, bumped only on breaking changes, schema file guarded by a test.
- **Terminal-Bench version (0031).** `terminal-bench@2.0` on Harbor 0.25.0, ATIF v1.8.

## Cross-questions

1. **Why is the headless stream the log itself?** One schema instead of two, and a consumer sees exactly what resume and export see. The cost is no token streaming. Answer: 0028.

2. **When does the schema version change?** Only on a rename, removal or change of meaning. New types and optional fields keep it, and consumers ignore what they do not know. The checked-in schema file still changes, which forces a reviewer to look.

3. **How does an unattended run answer an approval?** From the policy file. Anything left at "ask" is denied with a reason, or answered over stdin by a consumer that names the call id. It can never hang waiting for a human.

4. **Why read stdin on a daemon thread?** A blocking `readline` cannot be cancelled. On the default executor it would also hold up interpreter exit. A daemon thread dies with the process.

5. **What does Harbor's exec timeout actually kill?** The `docker compose` client on the host. The process inside the container survives, which is why we kill the group ourselves through a second exec. Answer: 0030.

6. **Why base64 the output?** Harbor decodes stdout with `errors="replace"`, so raw bytes would be corrupted before truncation could cut at a UTF-8 boundary. Base64 keeps them exact, so the container and local environments render identically.

7. **Why do writes use `upload_file` when reads use exec?** Output size is unlimited, but a single argv string is capped at 128 KiB on Linux, and a `bash -c` script is one string.

8. **How do you test container semantics without Docker in CI?** A fake container runs each exec as a local process and, like docker, kills only the client on timeout. The wrapper's kill path is what makes the leftover process die, so the test fails if that path breaks.

9. **Why run the agent on the host instead of in the container?** One install, the API key never enters the container, and every action already goes through the `Environment` interface. Terminus 2 runs the same way. Answer: 0031.

10. **What is the join key between our log, ATIF and later OTel?** The provider's call id. Our internal id never leaves the log. Answer: 0029.

11. **What can't ATIF hold?** Checkpoints, compaction and the system prompt text (the log stores only its hash). A trajectory is for evaluation, not for resume.

12. **What happens to the trajectory on a Harbor timeout?** `run` is cancelled, and the `finally` exports from the log as it is, dangling calls included. That works because ATIF is a projection rather than a second writer.

13. **The real run took 7 minutes. Is the harness slow?** No. Model requests took 435 of 442 s on NIM's free endpoint, and tools took 7 s, about 0.15 to 0.7 s per docker exec. Speed is an endpoint question for M6.

## Known gaps in M4

- Only one task, one attempt. The spec's protocol (oracle, a Terminus 2 baseline, at least 5 attempts) needs a faster endpoint and is M6.
- `HarborEnvironment` assumes GNU userland and bash in the image (0030).
- Run config does not yet record dataset version, Harbor version or attempts (spec section 10). M6 adds run configs.
- Headless mode has no `resume <id>`. Resume, fork and sessions are M5.
