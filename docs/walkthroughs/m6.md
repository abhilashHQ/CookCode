# M6 walkthrough and cross-questions

This document describes M6 as the code exists on branch `dev`. Read it with `docs/decisions/0035` to `0037` open, and 0022 for the 429 wait budget. Where a sentence names a function or file, it exists.

## 1. Map

- `evals/suite/<id>/`: 24 base tasks (6 each of bugfix, feature, refactor, investigate), plus 12 memory tasks added in M8. Each holds `task.toml`, `repo/`, a hidden `check.py`, `solution.sh` and, once recorded, `cassette.json`.
- `evals/suite.py`: `load_suite`, `SuiteTask`, `chains` (M8).
- `evals/runner.py`: `prepare` (fresh deterministic git repo), `run_check`, `run_solution`, `Run` (modes oracle, replay, record, live), `RunManifest`, `AttemptResult`, `work_dir`.
- `evals/stats.py`: `session_stats`, `repeat_streaks`, `cost`, `render`. Backs `cookcode stats`.
- `evals/variance.py`: `summarize` (score, per-round scores, bootstrap CI, within-task sd, paired MDE), `suite_trials`, `harbor_trials`, `infra_failure`.
- `evals/cli.py`: `cookcode eval run | report | context | repro`.
- `evals/tb-slice.txt` and `evals/run_tb.sh`: the Terminal-Bench slice and the runner for both agents.
- `providers/http.py`: 429s budgeted in seconds (`max_server_wait_s`), not attempts.

## 2. The parts worth reading closely

### `runner.py:prepare`
Copies the fixture into `work_dir(task, attempt)` and commits it as `main` with a fixed author date, then resets every mtime. Before this, `.git` object names and `ls -la` timestamps differed on every run, and replay showed drift on almost every request. The path is fixed too, so the workspace path in the system prompt matches between record and replay.

### Sequenced replay
`ReplayTransport(strict=False)` serves the recorded responses in order and reports each request's first difference as drift, with the text around the first differing character. A prompt change shows up as drift. A behavior change shows up as a failed check, because the replayed response no longer fits.

### `variance.py:summarize`
The score is the mean over tasks of each task's mean reward. The bootstrap resamples tasks, then attempts within each task (10,000 draws, fixed seed). The paired MDE is `(z.975 + z.8) * sqrt(2 * s_w^2 / (k * n))`, a floor because it ignores task-by-config interaction.

### `infra_failure`
A Harbor trial that died from provider exhaustion (429 after the budget) is excluded and listed by name, not scored 0. A score has to measure the agent, not the rate limiter. The exclusions are re-run from a worktree at the sweep commit and pooled.

## 3. The life of a suite attempt

1. `cookcode eval run --mode record --tasks bugfix-off-by-one-pagination`.
2. `prepare` builds the deterministic repo at `/tmp/harness-suite/<task>/1`.
3. The toolkit (`kit.py`, M8) builds tools for the run's strategy and features. The agent runs unattended (yolo) under the task's turn and wall caps.
4. The final assistant text is saved as the answer file. `check.py WORKDIR ANSWER` runs the hidden tests, which embed their own copy of the repo's tests, so weakening tests fails.
5. `results.jsonl` gets a row (pass, status, turns, wall), and the transport's tape is saved as the task's cassette.
6. Later, `cookcode eval run` (replay is the default) serves that tape with no network in about 2 s per task.

## 4. Acceptance

- Oracle: every task's solution passes its check and every unchanged fixture fails it (`validate.py`).
- First recording: 23 of 24 passed, 183 requests, 59 min (58.5 min of it model time). All 24 replay as PASS. The 2 tasks recorded before `prepare` pinned the branch name replay with drift notes and get re-recorded in the batch.
- Terminal-Bench, 10 tasks × 5 attempts, NIM MiniMax M3.1 Flash, 50-turn cap. Preliminary, before pooling the 2 fix-git re-runs: CookCode 0.800 (95% CI 0.62 to 0.96) against Terminus 2 0.725 (0.475 to 0.925). The paired MDE is about 0.26, so this is no detected difference. Final numbers are in 0036.
- `stats` over the 50 CookCode trials: 783 requests, 630 retries, 94% cache reads, 10% tool errors, 0 repeat streaks, 16,623 s of model time against 3,065 s of tools.

## 5. Gate decisions (owner, 2026-10-26)

- 24 tasks in four kinds, with sequenced cassettes (0035).
- The Terminal-Bench slice of 10 tasks, 5 attempts, both agents on the same endpoint (0036).
- Bootstrap CI plus paired MDE as the reporting method (0037).

## Cross-questions

1. **Why sequenced cassettes instead of strict ones for the suite?** A suite cassette holds a whole run, and the system prompt and tool schemas are in every request body. Strict matching would turn one prompt edit into 24 live re-records on free quota. Sequenced replay still catches behavior changes, as a failed check, and it reports prompt changes as drift.

2. **What can a sequenced replay miss?** A change that alters a request but happens to leave the recorded response still sensible. Drift is reported for every request, so it is visible, just not failing. Re-recording is the deliberate fix.

3. **Why fix the commit date and mtimes in fixtures?** Tool output contained `.git` object names and timestamps, so every request drifted, and drift stopped meaning anything. Determinism in the environment is what makes drift a signal.

4. **Why exclude 429-exhausted trials instead of scoring them 0?** They measure the provider's concurrency cap, not the agent. Harbor's own mean would score them 0. Exclusion is listed by trial name, and the excluded trials are re-run at the same commit, so nothing is hidden.

5. **Why bootstrap over tasks and then attempts?** Tasks differ far more than attempts do. Resampling only attempts would understate the uncertainty about what the agent does on tasks like these.

6. **What is the per-round score for?** It is what a single-attempt table would have reported. Its spread (0.70 to 0.90 for us) shows a reader how much one-shot leaderboards move on noise alone.

7. **Why a paired MDE, and why is it a floor?** Two configs run on the same tasks cancel task difficulty, so only attempt noise is left. It ignores task-by-config interaction, which adds variance, so the true detectable difference is larger.

8. **What did the aborted first sweep teach?** NIM's free tier allows 2 requests in flight per key and rejects the third instantly with no `Retry-After`. An attempt-count retry budget (about 15 s of waiting) ran out before any slot freed up. 429s are now budgeted in seconds (120 s).

9. **Why run both agents at the same time?** They see the same provider conditions. Running one after the other would confound agent differences with time-of-day load.

10. **Why does Terminus 2 go through litellm with `openai/<model>`?** It is the same NIM endpoint and the same model through an OpenAI-compatible path, so neither agent gets a different provider.

11. **What does a repeat streak count, and why did 0014 defer to it?** Three or more consecutive identical call-and-result pairs. 0014 refused to add a stuck-loop breaker without measuring loops first. 50 Terminal-Bench sessions produced zero streaks, so the breaker stays unbuilt.

12. **Why are wall caps 900 s when tasks finish in 3 minutes?** The early caps measured provider latency and 429 waits, and a run cut off by the clock replays differently, since replay is instant. Wall caps guard against hangs. The turn cap is the quota guard.

13. **Where does model time go against tool time?** 84% model, 16% tools on Terminal-Bench. A faster harness changes almost nothing, while a faster or less congested provider changes everything. That is why harness performance work was never a milestone.

14. **How does the suite stop a run from passing by deleting tests?** Checks embed their own tests and, for memory tasks, require the convention tests to still exist (`keeps`).
