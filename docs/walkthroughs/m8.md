# M8 walkthrough and cross-questions

This document describes M8 as the code exists on branch `dev`. Read it with `docs/decisions/0040` to `0043` open. Where a sentence names a function or file, it exists.

## 1. Map

- `core/features.py`: `Features` (jobs, verify_first, notes, facts, subagents, skills, hooks, mcp), all off by default, `parse`, `label`. The label is recorded in every suite manifest.
- `kit.py`: `toolkit(strategy, features, env, home=, memory_root=, settings=, spawner=)` returns a `Toolkit(tools, hooks, profile, hub)`. The CLI Runtime, the suite runner and the Harbor agent all compose their agents through it.
- `agent/hooks.py`: `Hook`, `HookContext`. `agent/loop.py`: `_blocked_call` (before gating), `_blocked_stop`, `_run_finish_hooks`, `_side_call`.
- `core/events.py`: `HookBlocked(hook, point, message, call_id)` and `RunConfig.hooks`.
- `tools/jobs.py`: `job_tools` (`job_start`, `job_check`).
- `tools/verify.py`: `repro_tool`, `registered`, `verify_first_hook`.
- `memory/store.py`: `FactStore`, `Fact`. `memory/layer.py`: `repo_key`, `fresh`, `consolidate`, `parse_facts`, `memory_parts`.
- `evals/suite.py`: the `memory` kind, `after`, `chains`. `evals/repro.py`: `judge`, backing `cookcode eval repro`.
- `evals/suite/memory-*`: 6 pairs.

## 2. The parts worth reading closely

### `loop.py:_dispatch` and `_blocked_call`
Hooks run before the approval gate. A blocked call gets its error result straight away and is logged as `hook_blocked`. It never starts, and the user is never asked about it. The live smoke run shows exactly this: `tool_call_started` 1, `hook_blocked` 1, for two attempted writes.

### `loop.py:_blocked_stop`
When the model ends its turn, each `before_stop` hook may return a message. The message is logged and rendered by the builder as a user note `[hook] ...`, and the loop takes another step. `max_stop_blocks` (3) caps this per run.

### `verify.py:registered`
It reads the log backwards for the latest ok `repro` result, so the lock state is a function of the log, the same as everything else. The `repro` tool runs the command and registers it only if it fails (`a_passing_command_does_not_register`).

### `jobs.py:_start_script`
`cd` into the tracked directory, `mkdir` the job dir, then `setsid bash -c RUNNER` in the background with output to a file. Then it waits up to 5 s for the pid file. The runner writes its pid, starts a watchdog that kills the group at `max_s`, runs the command and records the exit code.

### `layer.py:consolidate`
One side call (view `memory`) at the end of the run. The input is the existing fresh facts plus the transcript (capped at 60,000 chars). The output is JSON lines `{fact, paths, updates}`. Facts citing no existing file are dropped. Each fact is stored with the current hash of every cited file.

### `layer.py:fresh`
It rehashes the cited files on every read and splits facts into fresh and stale. Search results end with `(N stale facts left out: their files changed)`.

## 3. The life of a memory pair

1. `cookcode eval run --tasks memory-testenv-a,memory-testenv-b --features facts`. `chains()` puts A before B in attempt 1, both with memory root `out/memory/1`.
2. A: the agent fixes `Inventory.remove`, finds that tests only run through `run_tests.sh` (`APP_ENV=test`), and finishes. `on_finish` runs `consolidate`, which stores "tests run only through run_tests.sh, which sets APP_ENV=test" citing `run_tests.sh` and `config.py`, with their hashes.
3. B starts from a fresh copy of A's fixture. Same root commit, so same `repo_key` and same database. The profile at session start lists the fact, since both files still hash as recorded.
4. B's agent runs `./run_tests.sh` on its first try instead of discovering the convention.
5. The metric is B's pass rate, turns and tokens under none, notes and facts.

## 4. Acceptance

- Tests: hooks (tool blocks, stop blocks, cap), verify-first (lock, stop rerun, non-failing commands not registering, changed files without a repro, read-only turns), memory (updates retire, staleness, shared keys, consolidation into the next session, search without stale facts, notes), jobs (outliving the call, cwd, kill of the whole group, lifetime cap, wait cap, tail, bad ids).
- Every memory task passes its oracle and fails unchanged (`validate.py`: 36 tasks).
- Live batch (0036): verify-first (`vf-base` against `vf-on`, 6 bugfix tasks × 2) plus `eval repro`; memory (none, notes, facts × 6 pairs × 2); jobs on crack-7z-hash × 2.

## 5. Gate decisions (owner, 2026-10-27)

- Verify-first: hard lock.
- Fact memory: one end-of-session consolidation pass.
- Retrieval: a fixed profile plus a separate `memory_search` tool.
- Memory eval: paired suite tasks.

## Cross-questions

1. **Why put hooks before the approval gate?** A call the harness will refuse anyway should never cost the user a prompt. Gating first would ask "allow write to secrets.txt?" and then block it after a yes.

2. **How does a hook stay replayable when it runs code?** Its verdict is logged as `hook_blocked`, and the builder renders the request from that event. Replay never reruns the hook.

3. **What stops a stop hook from looping forever?** `max_stop_blocks` (3). After that the run ends, and the log shows the blocks.

4. **Why is verify-first a hard lock rather than a nudge?** Models skip a nudge when they think they see the fix, which is exactly when a reproduction matters most. The lock costs one tool call when the model would have complied anyway.

5. **Can the model cheat the lock?** Two ways. It can edit through bash, since only file tools are locked, and it can register a repro that fails for the wrong reason. `eval repro` catches the second offline: the repro must fail on the original code and pass on the reference solution.

6. **Why does the judge rebuild from the fixture plus the agent's created files?** It judges the reproduction, not the fix. Running the agent's test against the reference solution separates "the test was right" from "the fix was right".

7. **Why store facts with file hashes instead of TTLs?** A TTL guesses when a fact goes stale. A hash knows. Computing staleness on read means it cannot disagree with the files.

8. **Why consolidate at the end instead of letting the model write facts mid-session?** One call sees the whole session, can dedupe against existing facts and decide `updates`, and costs one request. Mid-session writes are decided by a model busy with the task. The notes arm tests that alternative.

9. **Why only a profile at session start and a search tool, never per-turn injection?** Per-turn injection changes the prompt every step and breaks the cached prefix (0038). Session start plus tools keeps the prefix stable.

10. **Why key memory by root commit?** Every clone, fork and eval copy of a repository shares its root commit, so the same codebase shares memory and different codebases never do.

11. **Why does task B start from A's fixture and not A's end state?** Otherwise B could pass from A's leftover edits, measuring the workspace and not memory.

12. **How do background jobs survive the call that starts them?** `setsid` puts the job in its own session, so the exec's process group kill on return does not reach it. All state is in files under `/tmp/cookcode-jobs/<id>`, which works the same inside a container.

13. **What if a job hangs forever?** The watchdog in its process group kills the group at `max_s`, at most 4 hours, and writes why.

14. **Why is every feature off by default?** The baseline must stay the harness that produced the M6 numbers. Each feature is an ablation arm, and the features label is recorded in every run manifest.

15. **What is `kit.py` for?** Three composition sites (CLI, suite runner, Harbor) each built tool lists by hand, and features would have meant three copies of the same switches. One function now builds the tools, hooks and system prompt additions. Putting it outside the tools package keeps the import boundary (tools may not import memory).
