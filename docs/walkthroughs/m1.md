# M1 walkthrough and cross-questions

This document describes M1 as the code exists on branch `m1-loop`, on top of M0. Read it with `docs/decisions/0009` to `0014` and `docs/experiments/chaos-m1.md` open. Where a sentence names a function or file, it exists.

## 1. Map and dependency rule

M1 adds two packages:

- `agent/` holds the loop and its pure helpers: tool contract, context builder, repair planner.
- `chaos/` holds the crash experiment: a scenario model, a worker that kills itself, and a driver that measures the result.

The rule for `agent/`: it may import `harness.__version__` and from `harness.core`, `harness.agent`, `harness.store.base`, `harness.providers.base` and `harness.env.base`. It may not import `harness.store.jsonl`, `harness.providers.fake`, `harness.env.local`, `harness.chaos`, `subprocess`, `socket`, `http`, `urllib` or `sys`, and it may not call `print`, `input` or `open`. `tests/test_boundaries.py` enforces this by parsing every file in `src/harness/agent/` with `ast`. It checks direct imports and call names, including method names such as `.open`. It does not follow transitive imports or dynamic imports.

The loop sees only protocols (`SessionLog`, `Provider`, `Environment`). The implementations are passed in, so the same loop runs against `FakeProvider` in tests and against a real provider later. `chaos/` is a client, so it may import everything, including `JsonlSessionStore` and `LocalEnvironment`. The repair planner is an injected callable (`repair_planner`, default `plan_repairs`), which is how the experiment swaps in the naive baseline without `agent/` knowing it exists.

No new runtime dependency. All serializable types are frozen pydantic models.

## 2. File by file

### `agent/tools.py`
`Tool[A]` is a frozen dataclass: `name`, `description`, `args_model` (a pydantic model class), `side_effect` (`read_only`, `mutating` or `external`) and an async `handler(args, ctx) -> ToolOutput`. `ToolContext` carries the environment, the cancel token, `cwd`, `timeout_s` and `max_output_bytes`. `ToolOutput` has `content`, `status` (`ok` or `error`), `exit_status` (`ok`, `error`, `timeout`, `killed`), and optional byte count and truncation flag. `ToolRegistry` keeps tools in insertion order.

Invariants: a duplicate tool name raises `ValueError`. The schema sent to the model comes from `args_model.model_json_schema()`, so validation and advertisement cannot disagree.

### `agent/context.py`
`build_request(events, ...)` projects the log into a `ModelRequest`. `UserMessage` and `SteerMessage` become user messages, `ItemEvent` becomes its item, and every other event type is dropped. `_reorder_results` then sorts each contiguous block of `ToolResult` items into the order of the `ToolCall` block before it. `estimate_tokens` is the length of the request JSON divided by four, a rough figure for the log.

Invariants: the function is pure, so the same events give the same request. Reasoning items pass through unchanged. Dropping reasoning that the current provider cannot replay is deferred to M5. Only the `raw` view exists.

### `agent/repair.py`
`unresolved_calls` returns every `ToolCall` item that has no `ToolResult` with its id. `plan_repairs` turns each into a `RepairAction`. `repair_bodies` turns actions into a `Repaired` event followed by a `ToolResult` item per call.

Status rule: no `tool_call_started` for the call gives `interrupted` ("not executed"). Started with `side_effect` `read_only` gives `interrupted`. Started with `mutating` or `external` gives `unknown`. If a `tool_call_finished` exists, its exit status is added to the reason.

Invariants: `side_effect` comes from the started event. A call that already has a result is never touched, so running repair twice changes nothing the second time. Repair never executes anything.

### `agent/loop.py`
`AgentConfig` (model, system prompt, `limits`, tool timeout, output cap, `max_parallel_tools`, `cwd`), `RunOutcome` (status, turns, usage, `last_seq`) and `Agent`. Public surface: `Agent.run(prompt, cancel=...)` and `Agent.steer(text)`.

Invariants:
- `run()` is not reentrant. A second concurrent call raises `RuntimeError`.
- `Agent.__init__` raises `ValueError` if `max_cost_usd` is set.
- `tool_call_started` is appended before the handler runs. Unknown tools and invalid arguments never run and write no started or finished event.
- A handler that raises `Exception` becomes an error result. A `CancelledError` is re-raised only when the run task itself is being cancelled (`Task.cancelling()`). Otherwise it becomes an error result, or a killed result if the run was cancelled.
- `tool_call_started` is appended with `durable=True`, so write-ahead does not depend on which store is plugged in.
- A mutating or external call that ends `killed` or `timeout` gets `unknown`.
- Steering left in the queue when a run ends is logged before its `session_finished`.
- Every call of a step has a result before the run ends, unless the process died or the task was hard-cancelled.
- The watchdog and link tasks are cancelled and awaited on every exit path, including exceptions.
- A failed log append is treated as a crash. Nothing more is written.
- A provider exception becomes `stop_reason="error"`, a non-retryable `ErrorEvent`, and a run that ends `error`. There is no retry in M1.

### `chaos/scenario.py`
`chaos_tools` builds two tools over one target file: `append_line` (`mutating`, runs `printf >> file` through `env.exec`) and `read_target` (`read_only`). An optional `after_effect` hook fires after a successful exec only. `naive_plan_repairs` marks every dangling call `interrupted` with the not-executed text. `ScenarioProvider` is a deterministic policy: from the request it classifies each wanted line as `confirmed`, `suspect` or `unconfirmed`. Any suspect line gives one `read_target` call. Otherwise it appends up to `per_step` unconfirmed lines, and when all are confirmed it says `done`. Only an `ok` read counts as evidence, and a line matches as a whole line.

Invariants: call ids are `scenario-NNNN`, derived from the request, so a crash run and a resume never collide. The constructor rejects duplicate, empty or multi-line target lines.

### `chaos/worker.py`
`ObservedLog` wraps a `SessionLog`, counts appends and fires a callback after each. `parse_point` reads `after_event:k` or `after_effect:i`. The worker runs the scenario and calls `os.kill(getpid(), SIGKILL)` right after the append of seq `k` returns, or right after the exec of the `i`th side effect. The module also holds the shared scenario constants (lines `L1 L2 L3`, two per step, 20 turns max).

### `chaos/checks.py`
`resolution_problems(events)` reports a seq gap, any unresolved call, and any call with more than one result.

### `chaos/experiment.py`
`reference_run` runs the scenario once without a crash and validates it. `enumerate_points` lists one `after_event` point per reference seq and one `after_effect` point per side effect. For each point `evaluate_point` runs the worker, checks the crash landed where intended, copies the crashed directory three times and verifies the copies are byte identical, then resumes one copy with `plan_repairs`, one with `conservative_plan_repairs` (no write-ahead records, every dangling mutating call `unknown`) and one with `naive_plan_repairs`. All resumes use a fresh provider and `run(None)`.

Invariants: the driver raises unless the worker died with return code -9. For `after_event:k` the crashed log's event kinds must equal the reference run's first `k+1` kinds. For `after_effect:i` the file must hold exactly the first `i` lines. A stray line in the output file raises. The expected set of naive duplicate points is derived from the reference log independently of the repair code, and the CLI exits 1 when the observed set differs.

## 3. The life of one step

This is the reference run in the chaos experiment: write `L1`, `L2`, `L3`, two calls per step. It has 22 events.

1. Seq 0 `session_started` (once, on an empty log), seq 1 `user_message`.
2. Boundary: drain steering, check cancel, check turns and tokens. All clear.
3. Seq 2 `model_request_started`. The request comes from `build_request` over the log.
4. Seqs 3 and 4 are `item` events, one per `ToolCall` as the stream finishes it. Seq 5 `model_request_finished` carries the stop reason and usage.
5. `_dispatch` validates both calls. Both are `append_line`, which is mutating, so `_batches` makes two single-call batches.
6. Seq 6 `tool_call_started`, fsynced. The handler runs `printf` through `env.exec`. Seq 7 `tool_call_finished`. Seq 8 the result `item`. Seqs 9 to 11 repeat for the second call.
7. Back at the boundary. The history now ends in results, so seq 12 starts the second request, which returns the third call (seqs 12 to 17). The third request (seqs 18 to 20) returns the text `done` with no calls.
8. The run ends `done`. Seq 21 `session_finished` with status, turns and summed usage.

With read-only calls the middle of step 6 changes: calls in one batch start together, so several `tool_call_started` events come first and results arrive in completion order.

## 4. The life of a crash and resume

Take the crash `after_effect:2`. The worker dies by SIGKILL right after the shell wrote `L2`, before `tool_call_finished`.

1. The log ends at seq 9, `tool_call_started` for the `L2` call. The file holds `L1` and `L2`. No close-out was written.
2. A new process opens the same session and calls `run(None)`. The log is not empty, so no `session_started`.
3. `plan_repairs` finds one call with no result. It has a started event with `side_effect="mutating"`, so the status is `unknown`.
4. The prologue appends a `repaired` event and a `ToolResult` with status `unknown` and the text "may have changed state before the session stopped. Inspect before retrying."
5. The loop builds a request. The scenario policy sees an `unknown` result for `L2` and no read after it, so the line is suspect, and it asks for `read_target`.
6. The read returns `L1` and `L2`. The line is confirmed. The policy appends `L3` and then says `done`.
7. Final file: `L1 L2 L3` once each, 3 requests.

The naive resume at the same point marks the call `interrupted`, so the policy appends `L2` again with `L3`. That is the duplicate. The log alone cannot tell this crash from `after_event:6`, which ends on the same event with an empty file.

A graceful interrupt skips all of this: the loop closes out the step itself, so the next `run()` finds nothing to repair.

## 5. The chaos results interpreted

Full text is in `docs/experiments/chaos-m1.md`. Summary:

- 25 crash points (22 events plus 3 side effects), three arms resumed from identical state.
  - Three-state repair: 0 duplicates, 0 missing, 25 of 25 clean resumes, 59 requests.
  - Conservative two-state: 0 duplicates, 0 missing, 25 of 25 clean resumes, 65 requests.
  - Naive two-state: 6 duplicates at 6 points, 0 missing, 25 of 25 clean resumes, 54 requests.
- Clean resume does not separate the arms. Safety separates naive from the other two. Cost separates the two safe arms: write-ahead saves 6 verify requests, all at points where a call was emitted but never started.
- The naive duplicates all fall after a side effect and before its result is logged: three after `tool_call_finished`, three right after the exec. A crash right after `tool_call_started` caused none when the effect had not run yet.
- Against naive, repair pays 5 extra requests, the verify reads after `unknown` results. Repair does not use `tool_call_finished` to skip the read.
- What it does not prove: SIGKILL keeps the page cache, so fsync under power loss is untested. The scenario model is a deterministic policy and not an LLM, so the 0 duplicates joins the repair rules with a policy that verifies before retrying. There is one scenario shape. The baseline lost no lines, so duplication is its only failure mode here.

## 6. Gate items and concerns for the owner

- **Parallel tool policy (0010).** Current: maximal runs of consecutive read-only calls run concurrently, cap 8 per step. Mutating and external calls run alone. Confirm or change.
- **Turn cap (0012).** 50 is provisional. Recommendation: keep it until M6 gives real turn counts.
- **Stuck-loop rule (0014).** Open. No rule exists. Recommendation: no rule in M1, test a nudge at M6, never stop outright.
- **Cooperative cancellation (0011).** A tool that ignores the token stalls a graceful interrupt and the wall-clock budget. There is no grace-period hard kill. Options: grace timeout then hard task cancellation (crash semantics), or accept it because every real tool goes through `env.exec`, which honors the token. Recommendation: accept for M1, add the timeout when the first tool or provider that bypasses the token appears.

## Cross-questions

**1. Why is the step the unit of work?**
Outside input needs fixed places to take effect. At a step boundary every call in the log has a result, so steering and budget checks cannot split a call from its result. The cost is latency of up to one step. Cancellation is the exception: it is checked inside steps as well.

**2. Why are results logged in completion order but sent in call order?**
The log records what happened, so a result is appended the moment its call finishes, and concurrency shows in the log. `build_request` sorts each block of results into the order of the calls before it, so the model sees one order whatever the timing was. Whether every provider accepts every such history, repaired results included, is not verified yet. The spec lists it as an open question for M3.

**3. Why does repair read the side effect from the log, not the registry?**
The registry says what the tools are now. Repair needs the class the call had when it started. The tool may have been renamed, reclassified or removed since the crash, or the resume may run a different build. The started event is the evidence recorded at the time, so the rule stays tied to it.

**4. What is the difference between an interrupt and a crash in this design?**
An interrupt is a request the loop sees. The loop closes out every call of the step, writes `interrupted` or `budget_exceeded` and `session_finished`, and the log needs no repair. A crash is the loop not being there: nothing is written, and the next `run()` applies the same status rule from the log. A hard `Task.cancel()` counts as a crash, because the loop does not try to write during cancellation.

**5. Why is the naive baseline fair?**
Both arms get the same loop, tools, scenario policy, crash point and byte-identical starting state. The only difference is the planner. The naive planner marks every dangling call `interrupted`, which is what a simple loop does to keep the history valid, and it passes every validity check. Its weakness is the information it throws away. A stronger baseline, the conservative planner, is measured too (question 16).

**6. What does the chaos test not prove?**
SIGKILL keeps the page cache, so fsync behavior under power loss is untested. The scenario model is a deterministic policy, so it says nothing about whether an LLM verifies before retrying. There is one scenario shape: sequential appends with a read tool that can verify them. The baseline lost no lines, so duplication is its only failure mode here, and a rule that wrongly reports an unrun effect as done is not exercised.

**7. Why fsync only `tool_call_started`, and what does a crash between the exec and `tool_call_finished` do?**
The intent has to be on disk before the effect, and the fsync also persists every earlier event. `tool_call_finished` and the result are separate, unsynced appends. A process crash keeps them in the page cache. After a power loss they may be gone, and repair then reports `unknown` from the started event, which is the safe answer.

**8. Why does repair mark a started mutating call `unknown` and not re-run it or call it failed?**
The log cannot tell a call killed before its exec from one killed after it. `after_event:6` and `after_effect:1` end on the same event, and only the file differs. Re-running risks a duplicate, and calling it failed risks a missing effect. `unknown` hands the decision to the model with "inspect before retrying", which is the unattended path of spec decision 10. The interactive "ask the user" path arrives in M3.

**9. What happens when a tool ignores the cancel token?**
Nothing stops it. The graceful interrupt and the wall-clock budget wait for the handler to return, because cancellation is cooperative. Only `Task.cancel()` from outside ends it, and that is crash semantics. Today every real tool uses `env.exec`, which honors the token. The first tool that does not is the trigger to add a grace timeout.

**10. How does the concurrency policy decide, and how can it be wrong?**
Consecutive `read_only` calls form one batch, capped at 8 at a time. Each `mutating` or `external` call is its own batch, and batches run in order. It is wrong when a tool is declared `read_only` and writes, since the class is trusted. It is also conservative: independent writes to different files still run one by one.

**11. Why does `run()` make its own cancel token?**
Two things can cancel a run, the caller and the wall-clock watchdog, and they mean different outcomes: `interrupted` and `budget_exceeded`. One internal token with first-reason-wins gives providers and tools a single thing to wait on, and the loop reads the reason. A watchdog firing never touches the caller's token, which the caller may reuse. The loop's own checks copy a cancelled caller token inward synchronously, so decisions do not depend on task scheduling.

**12. What do the budgets cover, and what do they miss?**
A turn is one model request, and failed requests count. Tokens are input plus output for this run. Wall clock is measured from the start of `run()`. Turns, tokens and elapsed time reset on every `run()`, the token check can overshoot by one request, and cost limits are rejected until M3 has prices.

**13. What happens to a steering message when the process crashes?**
If it was drained at a boundary, it is a `steer_message` in the log and survives. If it was still in the in-memory queue, it is lost and the client has to send it again. The queue lives with the `Agent` object, and nothing writes to the log at arrival time.

**14. How is the dependency rule enforced, and what does it miss?**
A test parses each file in `agent/` and rejects imports outside the allowed list and calls to `print`, `input` and `open`. It resolves relative imports against the package. It does not follow imports transitively and does not see dynamic imports. The planner and the environment are injected, so `chaos/` can replace repair with the naive baseline without `agent/` importing it.

**15. What does the verify read cost, and can it be avoided?**
Repair used 59 requests against 54, 5 more across 25 points, all verify reads after `unknown`. The read is paid only at a crash after `tool_call_started` and before the result is logged. Crashes elsewhere cost nothing extra. The read could be skipped when `tool_call_finished` exists with exit status `ok`, since the effect clearly completed, but the lost result might hold information the model needs, so M1 keeps the read.

**16. Why not skip write-ahead and mark every dangling mutating call `unknown`?**
That conservative rule is also safe: 0 duplicates over the same 25 points. It costs more, 65 requests against 59, because it also forces a verify read for calls that were emitted but never started, which write-ahead knows are safe to issue again. It also reads the side-effect class from the current registry, so a tool reclassified between the crash and the resume is repaired by the wrong rule, while `tool_call_started` records the class the call actually ran with.

## Known gaps in M1

- No grace-period hard kill for tools or providers that ignore the cancel token.
- Run provenance: `session_started` records the config of the first run only. A resumed run with a different model, tools or limits leaves no record, so `config_id` can misdescribe later runs, and budgets reset every `run()` with no session-wide bound. Fix before M4 and M6 depend on `config_id`.
- A mutating handler that raises after its side effect ran gets `error`, not `unknown`. Tools must return outcomes instead of raising; M2 tools catch their own errors.
- No retry for provider errors. Every provider failure ends the run as `error`.
- Steering in the memory queue is lost on a crash.
- Repair ignores `tool_call_finished` when choosing a status. It only adds the exit status to the reason.
- `run(None)` on a finished session still makes a request.
- A failed log append inside a concurrent batch surfaces as an `ExceptionGroup` and has crash semantics.
- If `Task.cancel()` hits `run()` a second time while it is cleaning up watchers, the watchers may finish after `run()` exits. The run is dying in that case.
- The concurrency and interrupt tests use real timing, with margins of 0.05 to 0.2 seconds. They passed 10 of 10 runs on an idle machine and could flake on a loaded one.
- Reasoning replay across providers is deferred to M5. The cost budget is deferred to M3.
