# M2 walkthrough and cross-questions

This document describes M2 as the code exists on branch `dev`, on top of M0 and M1. Read it with `docs/decisions/0015` to `0020` open. M1 is in `docs/walkthroughs/m1.md`. Where a sentence names a function or file, it exists.

## 1. Map and dependency rule

M2 adds one package and four modules in existing packages:

- `tools/` holds the tool set: `files.py` (read, write, edit), `search.py` (grep, glob), `bash.py`, and `default_tools()`.
- `agent/gate.py` is the permission gate. `agent/approval.py` holds the `Approver` protocol and two implementations. `agent/undo.py` restores checkpoints.
- `store/checkpoints.py` is the file-backed `CheckpointStore`. The protocol and `SnapshotRef` live in `store/base.py`.
- `env/base.py` gains `remove_file` and a `root` property (the absolute workspace path inside the environment), and `LocalEnvironment` implements both.

The rule for `tools/`: it may import `harness.core`, `harness.agent.tools`, `harness.env.base` and itself. It may not import `subprocess`, `socket`, `http`, `urllib` or `sys`, and it may not call `print`, `input` or `open`. All file and process access goes through the `Environment`. The rule for `agent/` gains two entries: it may not import `harness.tools` or `harness.store.checkpoints`. The tool set and the checkpoint store are injected (`ToolRegistry`, `Agent(checkpoints=...)`), so the loop knows only the `Tool` contract and two protocols.

`tests/test_boundaries.py` enforces both rules with one parametric `ast` scanner. It checks direct imports and call names, as in M1. It does not follow transitive or dynamic imports.

The gate sits in `agent/` and imports only `harness.core.events` and `harness.agent.tools`. It does not depend on any concrete tool. It reads a tool's `name`, `side_effect`, `args_model` and optional `touches`.

No new runtime dependency. All serializable types are frozen pydantic models. Schema changes are additive and `SCHEMA_VERSION` stays 1 (0020).

## 2. File by file

### `agent/tools.py`
M2 adds three things to the M1 contract. `Tool.touches` is an optional callable from validated arguments to the paths a call changes. It lets the gate and the snapshot step see the paths without running the handler. `ToolOutput.cwd` carries a working directory back to the loop. `workspace_path(root, cwd, path)` is the one path canonicalizer: it normalizes `join(root, cwd, path)` and returns the root-relative form when the result is inside the root (`.` for the root itself), the absolute form otherwise. Every spelling of a workspace file maps to one string. The file tools, the gate, the loop's snapshot step and drift check, and `undo` all call it with `env.root` (0018).

### `tools/files.py`
`read` returns numbered lines (`offset`, `limit` 2000), cuts lines over 2000 characters, stops at `max_output_bytes` with a hint that names the offset to continue from, and always returns at least one line. `write` creates parent directories and overwrites. `edit` is exact replacement (0015). All three catch their own exceptions and return error results, so a handler does not raise. `write` and `edit` are `mutating` and declare `touches`. `read` is `read_only`.

Invariants: a failed edit leaves the file byte-identical, because the write comes after every check and `LocalEnvironment.write_file` replaces the file atomically. CRLF survives an edit.

### `tools/search.py`
`grep` and `glob` are `read_only` tools over `env.exec` (0016). Both prefer `rg` and fall back to `grep` and `find`. The glob fallback translates the glob to a regular expression. Arguments are shell-quoted, and a test runs an injection string through every backend. `glob` enters its directory with `cd -- ./<path>` (absolute paths as given), so a path like `-P` or `-` is a directory name and never a `cd` option, `$OLDPWD` or a `CDPATH` lookup. It bounds its output inside the command: the listing is piped through `LC_ALL=C sort` and an `awk` that keeps the first 500 lines and prints the total count on a final line, which the tool parses. If the output still exceeds `max_output_bytes`, the tool returns an error with the count instead of a list, so the environment's truncation marker can never be read as a path.

### `tools/bash.py`
`bash` is `mutating`. It always execs at the root and starts with `cd -P -- <tracked cwd>`. If that fails, it prints a random per-call marker and exits before the command runs, and the tool returns the reset result (error, cwd `.`). Otherwise an EXIT trap prints a random sentinel and `pwd -P`. The tool strips that trailer, reports `workspace_path(root, ".", final)` on `ToolOutput.cwd`, and maps the exec result to a status: cancelled gives `killed`, timeout gives `timeout`, a non-zero exit gives `error` with `[exit code N]` appended (0019).

### `agent/gate.py`
`decide(...)` returns allow, deny or ask, plus the rule and the reason (0018). It takes the workspace `root` as a parameter. Around it: `Mode`, `Rule`, `Policy`, `GateDecision`, `subject` (the string a rule matches), `inside_workspace` (the canonical form is relative), `parse_rule`, `covers` (would this rule allow this call), `session_rules` (the extra allow rules, rebuilt from `approval_resolved` events with `allow_always`) and `split_command`, the bash lexer.

Invariants: the function does no I/O and is deterministic. Deny is checked first in every mode. File subjects are canonical, so a deny rule sees one spelling per file. Bash is judged per subcommand, allow rules match each subcommand's executed form (the words after leading assignments and prefix words), and a command the lexer cannot analyze asks outside `yolo`. If arguments fail validation, the gate uses the raw arguments and `auto-edit` never allows.

### `agent/approval.py`
`Risk` (the side-effect class, the rule that fired, the reason, the tracked `cwd`, and the canonical `subjects`: the paths, or the bash command), `Decision` (`allow`, `deny` or `allow_always`, with an optional reason and rule), the `Approver` protocol (`decide(call, risk, cancel)`), `PolicyOnlyApprover` (denies everything) and `ScriptedApprover` (a queue of decisions, for tests).

### `agent/loop.py`, M2 changes
- `AgentConfig` gains `mode` (default `ask`) and `policy`. `Agent` gains `approver` and `checkpoints`.
- `_prologue` appends `session_started` (empty log only), then `run_started`, then repairs, then the prompt.
- `_dispatch` resolves each call (unknown tool and invalid arguments become error results and are never gated), calls `_gate_all`, then batches the approved calls with the M1 policy.
- `_gate_all` gates in call order with one cwd read per pass. It stores the gated cwd on each approved call. `_gate` passes `self._env.root` to `decide`, fills `Risk.cwd` and `Risk.subjects`, and runs an `allow_always` answer through `_narrow`, which keeps the rule only if `covers` says it allows this call and otherwise logs a one-time allow.
- `_run_call` checks the cancel token, compares the call's subjects under the gated and current cwd, takes the snapshot, appends `tool_call_started` (fsynced), runs the handler, and appends `tool_call_finished` with the reported cwd and the result.
- `_current_cwd` is the last non-null `cwd` on a `tool_call_finished`, else `AgentConfig.cwd`.

### `store/checkpoints.py`, `agent/undo.py`
`FileCheckpointStore` keeps content-addressed blobs and one manifest per checkpoint (0017). After its renames it fsyncs the blob directory (when a blob was written) and then the store's root directory, so a durable `checkpoint_created` cannot outlive its manifest on a power loss. `undo` refuses a log with an unresolved tool call, canonicalizes every checkpoint path with `workspace_path`, loads before it writes, restores, and appends `checkpoint_restored`.

## 3. The life of a gated, checkpointed edit

Setup: mode `ask`, a scripted approver that allows, a checkpoint store, a file `a.py` containing `v0`. The user asks for `v1`, and the model emits one `edit` call. This is a new session.

1. Seq 0 `session_started`, seq 1 `run_started` (same config, same id), seq 2 `user_message`.
2. Boundary checks pass. Seq 3 `model_request_started`, seq 4 `item` (the `ToolCall`), seq 5 `model_request_finished`.
3. `_dispatch` validates the call against `EditArgs`. It is a known tool with valid arguments, so it goes to the gate.
4. The gate: `edit` is `mutating`, mode is `ask`, no rule matches, so the decision is `ask` with rule `mode:ask`. Seq 6 `approval_requested(call_id, risk="mutating", rule="mode:ask")`.
5. The loop awaits the approver and the cancel token together. The approver allows. Seq 7 `approval_resolved(allow)`.
6. `_run_call` re-checks the subjects. The cwd did not change, so they match.
7. The snapshot step canonicalizes `touches` (`a.py`) against the root and cwd, reads the file, saves a checkpoint, and appends seq 8 `checkpoint_created(paths=("a.py",), turn=1)`.
8. Seq 9 `tool_call_started`, fsynced. The handler runs and replaces the file atomically. Seq 10 `tool_call_finished` (`cwd` is null for file tools). Seq 11 the result `item`.
9. The next step starts at seq 12 with `model_request_started`, and the model sees the result.

The variants:
- `auto-edit`, edit inside the workspace: steps 4 and 5 collapse into one event, `approval_resolved(allow, rule="mode:auto-edit")`. No `approval_requested`, and the approver is never called.
- A read-only call in `ask` or `auto-edit`: no approval event at all. It goes straight to `tool_call_started`.
- A deny (a rule, or the approver): `approval_resolved(deny, reason)` followed by a result with status `denied`. No checkpoint and no `tool_call_started`.
- `allow_always`: the same events, with the approver's rule on `approval_resolved`, provided the rule covers this call. The next gate check rebuilds that rule from the log, so a later call it covers logs `approval_resolved(allow, rule)` and never reaches the approver. A rule that does not cover the call is logged as `approval_resolved(allow)` with no rule and the reason `allow_always rule <rule> does not cover this call; allowed once`.
- Several calls in one response: all are gated in call order first. Approvals for calls 2 and 3 are asked before call 1 runs. Then the approved calls run in batches under the M1 policy, each mutating call with its own snapshot and start.

Crash points:
- After `approval_resolved`, before `checkpoint_created`: no effect has happened. Repair finds no started event and marks the call not executed (0011), and the model issues it again. A test covers it.
- After `checkpoint_created`, before `tool_call_started`: the same, and the orphaned checkpoint holds bytes identical to the file, so undo through it changes nothing.
- After `tool_call_started`: the M1 rule applies. A started mutating call without a result is `unknown`.

## 4. Undo across turns

The test scenario in `tests/test_undo.py`, in `auto-edit` with a store. Turn 1 (`run("turn 1")`): two edits to `a.py`, `v0` to `v1` and `v1` to `v2`. Turn 2: `write` creates `b.py`. The log holds three `checkpoint_created` events with turns 1, 1 and 2. Their contents: `a.py` as `v0`, `a.py` as `v1`, and `b.py` as `None` (it did not exist).

1. `undo()` with the default `turns=1`. Open checkpoints are those no `checkpoint_restored` names. The last distinct turn is 2, so one checkpoint is selected. Its manifest says `b.py` did not exist, so `remove_file` runs. The log gets `checkpoint_restored(ids=(third,), paths=("b.py",), turns=(2,))`.
2. `undo()` again. Turn 2 is covered, the last open turn is 1. Both checkpoints are selected and the earliest per path wins, so `a.py` goes back to `v0`, not `v1`. The log gets a second `checkpoint_restored`.
3. A third `undo()` finds nothing open and returns `None`.

`undo(turns=2)` in one call gives the same final files with one event listing turns `(1, 2)`. All manifests load before the first write, so a missing or corrupt blob fails before any file changes.

Paths are canonical. If turn 1 edited `/abs/root/a.py` and then `a.py`, both checkpoints record `a.py`, the earliest wins, and undo restores `v0`. The first M2 build keyed by spelling, restored `v0` to the absolute path and then `v1` to the relative one, and left `v1`. Undo also canonicalizes paths read from older logs, so absolute keys from before the fix converge too.

Undo refuses a log with a tool call that has no result: `ValueError("undo needs every tool call resolved; resume the session first")`. It uses `unresolved_calls`, the same projection repair uses. Without the refusal, an undo after a crash appended its `[undo]` user message between the dangling call and the result that repair adds on the next resume, and providers that require a result right after its call would reject that request.

The model learns on its next run. The context builder renders each `checkpoint_restored` as a user message: `[undo] Restored b.py to their state before turn 2. File edits made in turns 2 are gone.` That message is the last user message of the next request. The conversation itself is untouched. Rewinding it is `fork`.

Because the open set is derived from the log, undo is the same after a resume with a fresh store object. A turn 3 after an undo gets its own checkpoints, and undoing it returns `a.py` to its turn 1 state.

What the scenario does not do: if the same turn also ran `echo c1 > c.txt` through bash, `c.txt` is not restored. The test for that case is in the same file.

## 5. Chaos under M2

The experiment now has 29 crash points. The reference run grew from 22 to 26 events: one `run_started` and one `approval_resolved(mode:yolo)` for each of the three mutating calls. Plus the 3 side effects, that is 29. The chaos worker runs in `yolo`, since the default `ask` mode with no approver would deny every append.

Results across the 29 points: the three-state repair and the conservative two-state repair both produced 0 duplicated and 0 missing side effects, and the naive repair still produced 6 duplicates at 6 points. The shape check holds: both safe repairs are clean at every point, and naive duplicates at exactly the points between a side effect and its result. The new approval events add crash points but no new kind of failure, since a crash between `approval_resolved` and `tool_call_started` leaves a call that never started.

`docs/experiments/chaos-m1.md` stays the M1 record with its 25 points. The M2 numbers are here only. The limits listed for M1 apply unchanged: SIGKILL keeps the page cache, the scenario model is a deterministic policy, and there is one scenario shape.

## 6. Review fixes

Each of these came out of review after the first build of its task, and each has a test.

- `read` stops at `max_output_bytes` with the continuation hint. The first build had no byte cap, so a file of long lines could return about 4 MB in one result.
- If the tracked cwd is deleted, bash does not run the command. It returns an error and resets the cwd to `.` through `tool_call_finished.cwd`. Before, the command ran from an unexpected place.
- A call whose gate subjects resolve differently because an earlier call in the same response changed the cwd is refused with `not run: the working directory changed to <cwd> after this call was gated, so its paths now resolve differently. Issue the call again.`
- Mode and policy are in `RunConfig`, so a mode change between runs changes `config_id` on `run_started`.

The final review of M2 found two critical and four important issues, plus minor ones. Each fix has a test, most of them the reviewer's probe scenarios turned into tests in `tests/test_workspace_root.py`, `tests/test_gate.py`, `tests/test_tools_bash.py`, `tests/test_tools_search.py` and `tests/test_undo.py`.

- **Executed-form allow matching (C1).** `bash:pytest*` allowed `pytest=1 rm -rf victim`. Allow rules now match each subcommand's executed form, and a suspicious leading assignment blocks a rule-based allow. Cross-question 16 explains the bug.
- **Root canonicalization (C2, I1, I2).** `Environment.root` and `workspace_path` replace the bash tool's root inference and the gate's root-blind normalizer. Leaving the workspace and returning gives a relative cwd again, every spelling of a denied file is denied, and undo converges aliased checkpoints.
- **Undo refuses unresolved logs (I3).**
- **The approver sees `cwd` and `subjects` (I4).**
- **`allow_always` must cover its call (M4).**
- **glob `cd --` and in-command bounds (M1, M2).** Bash's tracked-cwd `cd` uses the same explicit `./` form, which closes `$OLDPWD` and `CDPATH` lookups that `--` alone does not.
- **Checkpoint directory fsync (M5).**
- **Partial undo stays a known gap (M3).** See the list at the end.

## 7. Stage 1 summary

M2 closes Stage 1: the harness core, with `FakeProvider` only. These are the guarantees the code gives now, and where each is recorded.

**The log is the truth.** Every fact is an event in an append-only log (0001) with an envelope that survives schema growth (0002, 0020). A torn last line is repaired on open and `tool_call_started` is fsynced (0003). Secrets are redacted before they reach disk (0004), with one exception: checkpoint blobs are not redacted (0017).

**Every tool call ends with exactly one result.** The loop appends a result for every call of a step, and a resume repairs the rest by one rule that reads the evidence recorded at the time (0009, 0011). Repair never re-executes a call. The chaos experiment measures this: 0 duplicates and 0 missing at 29 crash points, against 6 duplicates for the naive baseline.

**Every call is gated before it runs, and the decision is logged.** The gate is a pure function (0018). The `Approver` sits behind a protocol, and a cancel during an approval wait ends the wait. A denied call never starts.

**File edits are reversible per turn.** A checkpoint is taken after approval and before the call starts (0017). Undo restores files and tells the model. Bash side effects are outside it.

**Session state is a projection of the log.** The working directory (0019), the "always allow" rules (0018) and the set of undone checkpoints (0017) are all rebuilt from events. A resumed or reopened session has them. A run's config, including mode and policy, is recorded on `run_started` (0020).

**Work is bounded and interruptible.** Cooperative cancellation, a wall clock, a turn cap and a token budget (0007, 0011, 0012). Steering lands at step boundaries (0013). Read-only calls run concurrently and everything else runs alone (0010).

**The core stays free of I/O.** `agent/` and `tools/` reach the world only through protocols, and an AST test enforces the import rules.

What Stage 1 does not guarantee:
- It is not a security boundary (0018). The OS sandbox is M10 and Flagship 2.
- No real provider has been run. What each API accepts for repaired results is open until M3.
- No provider retry. Any provider error ends the run.
- The stuck-loop rule is open (0014).
- Durability under power loss is untested, since SIGKILL keeps the page cache.

Stage 2 starts at M3 with a real adapter and a CLI that supplies an `Approver`.

## 8. Gate items and concerns for the owner

- **Edit format (0015).** Proposed: exact string replacement. Confirm, or ask for a patch tool next to it. Recommendation: confirm, and measure the failed-edit rate at M6.
- **grep and glob placement (0016).** Proposed: tools on `env.exec` with a `grep` and `find` fallback. Recommendation: confirm. The fallback differs from `rg` on `.gitignore`.
- **Snapshot method (0017).** Proposed: file copies behind a `CheckpointStore`, not an `Environment` method and not a git shadow repo. Recommendation: confirm. Revisit if M6 shows models changing files through bash often.
- **The gate is defense in depth (0018).** Not a gate decision, but the owner should hold this line in any claim about safety: deny rules are text matches, and a real boundary needs the OS sandbox.
- **The default mode.** `ask` with no approver denies every mutating call. That is the safe default for a library, and it means every client must supply an approver or a mode.

## Cross-questions

**1. Why is "always allow" stored in the log?**
Because the answer to "may this run without asking" must be the same after a resume as before it. If the rule lived in the approver's memory, a restart or a second client would ask again, or worse, would not know which calls the user already cleared. The log already records the approval event, so the rule rides on `approval_resolved.rule` and `session_rules` rebuilds the set on every gate check. That keeps the gate a pure function of values. The cost is one extra read of the log per gated call, and rules cannot be revoked short of editing the log.

**2. Why split bash commands before matching rules?**
A rule like `bash:ls*` matches the string `ls; rm -rf ~`. Matching the whole line would let one allowed word carry anything after it, and a deny rule for `rm -rf*` would miss `cd x && rm -rf y`. Splitting means a deny fires if any piece matches, and an allow applies only if every piece matches. The price is a lexer for quotes, wrappers, substitutions and redirections, and the lexer is partial by nature. Anything it cannot analyze asks.

**3. Is the gate a security boundary?**
No. Deny rules are text matches. `rm -r -f` and `rm --recursive --force` get past `bash:rm -rf*`. Interpreter one-liners are not closed, so `python -c`, `perl -e`, `node -e`, `make` and `npm run` can do anything the model can write. Allowing a test runner already allows the code the model put in the tests. The gate stops accidents and obvious forms, and it makes each decision visible. The boundary is an OS sandbox as an `Environment` wrapper, planned for M10 and Flagship 2. Until then, `yolo` belongs in a container.

**4. Why is snapshotting not an Environment method?**
The spec sketched `Environment.snapshot`. It would make every environment, a local directory, a Harbor container and a remote sandbox, implement storage and restore. File copies need only what the protocol already has: read a file, write a file, and one remove method added for undo. The loop reads the bytes through the environment and a host-side `CheckpointStore` keeps them, content-addressed. The same code runs everywhere. The cost is that the host stores copies of a sandbox's files, and that only files a tool declares through `touches` are covered.

**5. What does undo not cover?**
Bash side effects: anything a command changed, created or deleted outside the `touches` of a write or edit. Symlinked targets are followed, not detected. Files the model never touched with `write` or `edit`. It also does not rewind the conversation, which is `fork`. It can be partial if a write fails midway (earlier files restored, nothing logged, a rerun is safe). And the blobs it restores from are not redacted, so the checkpoint directory is as sensitive as the workspace.

**6. Why is the working directory logged state?**
Each bash call is a fresh process, so the shell cannot remember it. Keeping it in a live object would lose it on resume and hide it from the log. Instead the tool reports where the command ended, the loop writes that on `tool_call_finished.cwd`, and the current cwd is the last recorded value. A resume, a fork and a second client all see the same directory. Bash is always `mutating`, so its calls never overlap and a `cd` is in the log before the next call starts. Environment variables do not persist, and the tool description says so.

**7. Why gate all calls of a response before any executes, and what breaks?**
It gives one ordered stream of approvals with no interleaving between a person's decisions and tool output, and a denied or cancelled response never half-runs. What breaks is the cwd: the gate judges later calls against the directory as it was before the response started. An approved `cd ..` followed by `edit x.txt` is judged inside the workspace and would run outside it. `_run_call` compares the call's subjects under the gated and the current cwd and refuses the call if they differ. The model reissues it, and the gate judges it again.

**8. Why does the checkpoint come after approval and before `tool_call_started`?**
Approval first, so a denied call leaves no checkpoint. Checkpoint before start, so a started call always has its pre-image on disk and in the log. If the process dies in between, no effect has run, repair marks the call not executed, and the checkpoint is harmless because it matches the file. A start before the checkpoint would allow a crash with an effect and no way back.

**9. Why is undo visible to the model, and why does it not rewind the conversation?**
After an undo, the model's history says it edited files that no longer have those edits. A model that believes its edits exist will build on them. So `checkpoint_restored` is a model-layer event and the context builder turns it into a user message that names the files and turns. Rewinding the conversation is a separate act, `fork --at <seq>`, as in other agents' rewind features. Keeping them apart means a user can restore files and keep the discussion, or the reverse.

**10. What happens if a cancel arrives while the harness waits for an approval?**
The wait races the approver against the run's cancel token, and cancel wins even if the approver answered at the same moment. No `approval_resolved` is written, because no decision was made. `approval_requested` stays in the log with no resolution. Every call of the response that has not started gets the M1 not-executed close-out, and the run ends `interrupted`. An `allow_always` given at the same instant as a cancel is lost. The tasks for the approver and the token are both cancelled and awaited, so none leak.

**11. Why exact-match edits, and when would I switch?**
Exact replacement has precise failures: not found, found N times, whitespace differs. Each tells the model what to do, and a failed edit leaves the file untouched. A patch format saves tokens on multi-hunk changes and may match model training, but it adds a parser and partial-apply cases. This is a proposed decision for the gate (0015). I would switch, or add a second tool, if the M6 suite shows a high failed-edit rate for a model that does better with patches.

**12. Why are grep and glob tools on exec and not Environment primitives?**
A smaller `Environment` is cheaper for every future environment to implement, and `exec` already runs `rg` or `grep` anywhere with a shell. The tool prefers `rg` and falls back to `grep` and `find`. The costs are quoting, which an injection test covers, and a fallback that ignores `.gitignore` and matches `--include` on file names only. The alternative, a primitive per search, is in 0016. This is also a proposed decision.

**13. How does an old reader handle the new events and fields?**
New event types (`run_started`, `checkpoint_restored`) fall into `OtherEvent` and are kept as data. New optional fields on known types (`cwd`, `mode`, `policy`) are dropped in memory by an old reader and kept on disk by `fork`, which copies raw bytes. An old context builder would not render `checkpoint_restored`, so it would not tell the model about an undo. New code reads old logs with defaults. `config_id` values before and after M2 are not comparable, since the hash now covers `mode` and `policy` (0020).

**14. Why are mode and policy in `RunConfig`, and what does `run_started` fix?**
M1 recorded the config once, at `session_started`, so a resumed run with a different model or limits left no trace and `config_id` could describe the wrong run. Every `run()` now appends `run_started` with its config and id. Mode and policy are part of that config because they change what the agent may do. A run in `yolo` and a run in `ask` should not share an id. Budgets stay per run (0012).

**15. Why is `tools/` a separate package from `agent/`?**
`agent/` is the generic loop and knows only the `Tool` contract. The six tools are one tool set. MCP tools in M10 would register through the same contract, and the loop would not change. The boundary test forbids `agent/` from importing `harness.tools`, so the separation holds. It also keeps the loop free of file and process code: `tools/` is limited to the environment protocol and cannot call `open` or import `subprocess`.

**16. What was the assignment-prefix bug, and why did per-subcommand raw matching miss it?**
With `bash:pytest*` allowed, the model could run `pytest=1 rm -rf victim`. The lexer split it into one subcommand whose raw text starts with `pytest`, so the allow rule matched. Bash reads `pytest=1` as an environment assignment for the command that follows and runs `rm -rf victim`. `+=` and subscripts (`ls[0]=x`) work the same way. Splitting into subcommands fixed the compound case (`ls; rm`), but it still compared a rule with text, and the text of a subcommand is not the command it runs. The deny path already knew this: `_forms` strips leading assignments and prefix words before matching. The allow path did not use it, so the two sides judged different strings. Allow now matches the executed form, the same words bash will run, and refuses a rule-based allow when a leading assignment is suspicious. The lesson I take from it: a rule must be matched against what will execute, and an allow path has to be at least as strict as the deny path about what that is.

## Known gaps in M2

- Bash side effects are not covered by undo.
- Symlink escapes are not detected. A path that is a link out of the workspace is read, written, snapshotted and restored at its target, and `auto-edit` treats it as inside.
- `grep`'s fallback ignores `.gitignore`, and its `--include` matches file names only.
- A cancel during an approval wait logs no `approval_resolved`. The request stays unresolved in the log.
- Checkpoint blobs are not redacted. They can hold secrets that the event log would have removed.
- `allow_always` rules for compound bash commands do not cover the call they were given for, so they are downgraded to a one-time allow. No rule synthesis exists.
- Deny rules are text matches and interpreter one-liners are not closed (0018).
- Reads outside the workspace are allowed in every mode. Only a deny rule guards them.
- Undo is not atomic (final review M3). If a write fails midway, earlier files are restored and later ones are not, no `checkpoint_restored` is appended, and the model is not told. Retrying `undo` re-applies the same selection, so a rerun is safe. If the user carries on instead, the partial restore stays invisible. The fix would be an intent event or a restore manifest that a retry or the next `run()` completes or reports.
- A command that sets its own `EXIT` trap loses the cwd update for that call.
- Nothing prevents calling `undo` while a run is active. The unresolved-call refusal catches it while a call is in flight, and nothing catches it between calls. Undo must not run concurrently with `run()`.
- Glob errors out when its 500 bounded paths still exceed `max_output_bytes`. With long paths and the 30000 default that can happen, and the model has to narrow the pattern.
- `SnapshotRef` is defined and unused.
- The M1 gaps that stay open: cancellation is cooperative only, with no grace-period hard kill, and steering held in the in-memory queue is lost on a crash. The other M1 gaps in `docs/walkthroughs/m1.md` stand as written, except run provenance, which `run_started` closes.
