# M10 walkthrough and cross-questions

This document describes M10 as the code exists on branch `dev`. Read it with `docs/decisions/0047` to `0050` open. Where a sentence names a function or file, it exists.

## 2. The parts worth reading closely

### `config.py:over`
It merges two `Settings`. Scalars: the top value if set, else the bottom. `allow`, `deny` and `hooks` concatenate. `mcp.servers` merge by name, top winning. `load_settings` applies it to user, then repository, and the CLI then layers environment, resumed session and flags on top.

### `mcp.py:_Server`
The SDK's `stdio_client` and `ClientSession` are async context managers that must be entered and exited in the same task. Each server is owned by a task that enters them, lists the tools, sets a ready event, then waits on a close event. Calls go to the session from any task. `aclose` sets the close event and awaits the owner, so exit happens in the right task.

### `agent/tools.py:loaded_tools`
A pure function of the log: the names from every successful `tool_search` result. The loop calls it in `_build`, so the request's tool list is the always-on tools plus the loaded deferred ones. Replay calls the same function on the same log.

### `mcp.py:_passthrough`
MCP servers describe their arguments in JSON Schema, not Pydantic. A passthrough model accepts any object and reports the server's own schema, so the model sees the real schema and the server validates.

### `tui.py:_PaneWriter`
A `StringIO` whose writes are split into lines and pushed into the `RichLog` with ANSI colors parsed. `Display` writes to it as if it were a terminal, so the TUI reuses every rendering decision of the plain CLI.

## 3. The life of a deferred MCP call

1. `.cookcode/settings.toml` declares `[mcp.servers.calc]`. The user runs `cookcode --features mcp -p "add 17 and 25 with the calc server"`.
2. `toolkit` starts the hub. The owner task connects and lists `add` and `explode`. Both are registered as deferred tools `mcp__calc__add` and `mcp__calc__explode`.
3. The system prompt lists their names and descriptions. The request's tools are the built-ins plus `tool_search`, with no MCP schemas.
4. The model calls `tool_search(names=["mcp__calc__add"])`. The result confirms the load.
5. The next `_build` runs `loaded_tools(events)`, which returns `{"mcp__calc__add"}`, so its schema is in the request.
6. The model calls `mcp__calc__add(a=17, b=25)`. It is external, so ask mode would ask. The hub forwards it and returns `42`.
7. On exit the Runtime's `aclose` closes the hub, and each owner task exits its context managers.

## Cross-questions

1. **What is the precedence order, and why that order?** Flag, resumed session, environment, repository, user, preset. The most specific and most recent intent wins: a flag typed now beats a session's recorded config, which beats ambient environment, which beats shared files.

2. **Why do rule lists add up instead of overriding?** A repository's settings must not be able to drop a user's deny rules. Adding up plus deny-wins in the policy means every layer can only tighten what it denies.

3. **What was the policy bug?** `run_cli` built a policy and passed it to the Runtime, which skipped merging the settings' rules when given one. Allow and deny from settings were silently ignored in the interactive CLI. The merge now happens inside the Runtime on every path, and a test covers it.

4. **Why defer MCP schemas?** A server can expose dozens of tools at hundreds of tokens each, sent on every request. Deferral pays one line per tool, plus schemas only for the tools used.

5. **When is deferral worse?** A session that uses one MCP tool once pays an extra step to load it. Deferral pays off as servers and tools grow.

6. **Why must the loaded set come from the log?** The request's tool list is part of what replay must rebuild exactly. If the hub held it, replay would need the hub and its history. `loaded_tools` makes it a pure function of events.

7. **Why one owner task per server?** The SDK's context managers must exit in the task that entered them, or anyio raises. An owner task makes entry and exit happen in one place no matter which task makes calls.

8. **Why did errors need `_cause`?** SDK 2.x raises from inside task groups, so a failed connect arrives as an `ExceptionGroup` that names nothing useful. `_cause` unwraps it to the innermost error.

9. **Why stdio only?** Local servers cover the showcase, and stdio needs no auth or network handling. Streamable HTTP is a transport behind the same hub.

10. **Why are MCP tools external, and what does that change?** They run code the harness has never seen. In ask mode every call is asked, and policy rules apply by name.

11. **Why build the TUI as another observer instead of a new client?** 0026 already made clients decorate one runtime. The TUI reuses `Display` through `_PaneWriter`, so it adds no event handling and cannot drift from the plain CLI.

12. **How does steering work in the TUI?** Text typed while a run is active becomes a steer message, applied at the next step boundary (0013), the same as in the plain CLI.

13. **Why keep `harness_version` and `harness_commit` after the rename?** They are stored field names in every log and cassette. Renaming them would invalidate stored data for a cosmetic gain. A schema v2 is the time to change them.

14. **Why are Textual and MCP optional extras?** A Harbor container needs neither. The dev group includes both so CI runs their tests.
