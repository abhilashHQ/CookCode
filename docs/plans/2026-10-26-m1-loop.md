# M1 Agent Loop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A durable agent loop on top of M0. It runs steps, dispatches tools with a concurrency policy, takes steering input at step boundaries, enforces budgets, handles interrupts gracefully, and repairs crashed sessions on resume. The chaos experiment proves the repair rules against a naive baseline.

**Architecture:** A new `cookcode.agent` package holds the loop and its pure helpers (context builder, repair planner, tool contract). It depends only on M0 protocols (`SessionLog`, `Provider`, `Environment`), never on their implementations. A separate `cookcode.chaos` package is a client that crashes the loop at every event boundary and measures side-effect duplication.

**Tech Stack:** Same as M0. No new runtime dependencies.

**Spec:** `docs/specs/2026-10-22-flagship1-design.md`, sections 3, 4.2, 4.3, 4.5, 5, 6, 7 (raw strategy only), 13 row M1, 14 items 7 and 10.

**Style of this plan:** this plan gives architecture calls, exact interfaces, invariants and behavioral tests. It contains no implementation code. Implementers write the tests and the code. Every listed test is required. Test names are suggestions, and the asserted behavior is binding.

## Architecture calls (made here, recorded in Task 8)

1. **Package placement.** The loop lives in `cookcode.agent`, separate from `cookcode.core`, because it orchestrates I/O through protocols while `core` stays pure types. Dependency inversion is enforced by the boundary test.
2. **A step is the unit.** A step means: drain steering, check budgets, build the request, stream, log items, run the response's tool calls, log the results. Steering and budget checks happen only at step boundaries, so a call/result pair is never split.
3. **Turn = one model request.** `max_turns` counts model requests in this run. The provisional default is 50, decided at the M1 gate.
4. **Tool concurrency.** The response's tool calls are split, in call order, into maximal runs of consecutive read-only calls (each run executes concurrently, capped by `max_parallel_tools`) and single mutating or external calls (each executes alone). Batches run in order.
5. **Results are logged in completion order.** The log records what actually happened. The context builder reorders each block of results into call order when it builds a request.
6. **Write-ahead.** `tool_call_started` is appended (fsynced by `DURABLE_TYPES`) before a handler runs. Unknown tool names and invalid arguments never execute: they get an error `ToolResult` with no `tool_call_started` and no `tool_call_finished`.
7. **Interrupt and crash are different paths.** On a graceful interrupt, the loop closes out every call of the current step itself, so the log needs no repair. Repair runs only for crashes and hard task cancellation. Both paths use one status rule: a call that never started is `interrupted` ("not executed"); a started read-only call that did not complete is `interrupted`; a started mutating or external call that did not complete is `unknown`.
8. **Side-effect class comes from the log.** Repair reads `side_effect` from `tool_call_started`, never from the current tool registry, which may have changed since the crash.
9. **Cancellation is layered.** `run()` creates an internal `CancelToken`. The caller's token and a wall-clock watchdog both cancel it, with reasons `"user"` (or whatever the caller passes) and `"wall_clock"`. Providers and tools see only the internal token. The reason decides whether the run ends `interrupted` or `budget_exceeded`.
10. **Hard cancellation equals a crash.** If the task running `run()` is cancelled with `Task.cancel()`, the loop does not try to write close-out events. The `CancelledError` propagates, and the next `run()` repairs the log.
11. **Cost budget is not enforced in M1.** There is no price table until M3. If `Limits.max_cost_usd` is set, `Agent.__init__` raises `ValueError("cost limits need pricing, which arrives in M3")`.
12. **Session lifecycle.** `session_started` is written once, on the first run of an empty log. Every `run()` call ends with its own `session_finished`. A later `run()` continues the same log after it.
13. **Unknown-outcome policy (spec decision 10).** M1 implements the unattended path only: the repaired `unknown` result tells the model to inspect before retrying. The interactive "ask the user" path arrives with the CLI in M3.
14. **Reasoning replay** (dropping reasoning that is not replayable to the current provider) is deferred to M5 with adapter B. The M1 builder passes items through unchanged.
15. **Chaos crash points are enumerated, not random.** The experiment crashes after every event and after every side effect of a reference run, so coverage is exhaustive and reproducible.

### Task 1: Tool contract and registry

**Files:** create `src/cookcode/agent/__init__.py` (empty), `src/cookcode/agent/tools.py`, `tests/test_agent_tools.py`. Modify `tests/test_boundaries.py`.

**Interfaces (produces):**
- `ToolContext`: a frozen dataclass with `env: Environment`, `cancel: CancelToken`, `cwd: str`, `timeout_s: float`, `max_output_bytes: int`.
- `ToolOutput(content: str, status: Literal["ok", "error"] = "ok", exit_status: Literal["ok", "error", "timeout", "killed"] = "ok", output_bytes: int | None = None, truncated: bool = False)`: a frozen pydantic model. When `output_bytes` is `None`, its effective value is `len(content.encode())`. Expose that as a property `size`.
- `Tool`: generic over its args model `A` (a pydantic `BaseModel`). It has `name: str`, `description: str`, `args_model: type[A]`, `side_effect: SideEffect` (from `cookcode.core.events`), and `handler: Callable[[A, ToolContext], Awaitable[ToolOutput]]`. It has a method `schema() -> ToolSchema` whose `parameters` come from `args_model.model_json_schema()`.
- `ToolRegistry(tools: Iterable[Tool[Any]])` provides:
  - `get(name) -> Tool[Any] | None`
  - `schemas() -> tuple[ToolSchema, ...]` in registration order
  - `names() -> tuple[str, ...]`
  - a duplicate name raises `ValueError`
- Handler contract: a handler honors `ctx.cancel`. When cancelled, it returns early with `exit_status="killed"` and whatever partial content it has. It does not raise `CancelledError` for token cancellation. Any other exception is a tool bug, which the loop converts to an error result.

**Behavioral tests:**
- `schema()` of a tool whose args model has `path: str` and `limit: int = 10` yields that tool's name and description, and parameters with both properties, of which only `path` is required.
- Registry: lookup by name works, an unknown name gives `None`, schemas keep registration order, and duplicate names raise `ValueError`.
- `ToolOutput(content="héllo").size == 6`, and an explicit `output_bytes` wins.
- Boundary: the extended boundary test fails if any file under `src/cookcode/agent/` imports `cookcode.store.jsonl`, `cookcode.providers.fake`, `cookcode.env.local`, `cookcode.chaos` or a forbidden I/O module, or calls `print`/`input`/`open`. Prove that it catches a violation by checking the scan function against a small in-memory source string, not by planting a bad file.

**Commit:** `feat(agent): tool contract and registry`

### Task 2: Raw context builder

**Files:** create `src/cookcode/agent/context.py`, `tests/test_context.py`.

**Interfaces (produces):**
- `build_request(events: Sequence[Event], *, model: str, system: str, tools: tuple[ToolSchema, ...], max_output_tokens: int | None = None) -> ModelRequest`
- `estimate_tokens(request: ModelRequest) -> int` = `len(request.model_dump_json()) // 4`

**Rules:**
- The builder uses only model-layer events, in log order:
  - `UserMessage(text)` becomes `text_message("user", text)`.
  - `SteerMessage(text)` becomes `text_message("user", text)`.
  - `ItemEvent(item)` becomes `item`.
  - Internal events are ignored.
- **Result reordering.** Take each maximal run of consecutive `ToolResult` items in the projected sequence. Order the run by the index of its `call_id` among the `ToolCall` items of the nearest preceding block of consecutive `ToolCall` items. Results whose `call_id` is not in that block keep their relative order and go after the matched ones.
- The function is pure, so calling it twice on the same events gives equal requests.

**Behavioral tests:**
- An empty log gives a request with no items, the given model/system/tools, and `max_output_tokens` passed through.
- User, steer, item and internal events: only the model-layer ones appear, in order, and steer appears as a user message.
- Calls A, B, C followed by results in the order C, A, B: the built request has results A, B, C.
- Two separate steps, each with calls and out-of-order results: each block is reordered against its own calls only.
- A result with an unmatched `call_id` stays after the matched results of its run.
- Purity: two calls give equal results, and the input sequence is not mutated.
- `estimate_tokens` is positive and grows when an item is added.

**Commit:** `feat(agent): raw context builder with result reordering`

### Task 3: Repair planner

**Files:** create `src/cookcode/agent/repair.py`, `tests/test_repair.py`.

**Interfaces (produces):**
- `RepairAction(call_id: str, tool: str, status: Literal["interrupted", "unknown"], reason: str)`: frozen.
- `unresolved_calls(events: Sequence[Event]) -> list[ToolCall]`: every `ToolCall` item without a `ToolResult` item carrying its `id`, in log order.
- `plan_repairs(events: Sequence[Event]) -> list[RepairAction]`: one action per unresolved call, in log order.
- `repair_bodies(actions: Sequence[RepairAction]) -> list[EventBody]`: for each action, `Repaired(call_id, status, reason)` followed by `ItemEvent(item=ToolResult(call_id=..., status=..., content=reason))`.

**Classification (exact reason strings, binding):**

| Log state of the call | status | reason |
|---|---|---|
| No `tool_call_started` | `interrupted` | `not executed: the session stopped before this call ran. Safe to issue again.` |
| Started, side effect `read_only`, no result | `interrupted` | `interrupted: the call started but its outcome was not recorded. It is read-only, so it is safe to retry.` |
| Started, side effect `mutating` or `external`, no result | `unknown` | `unknown: the call started and may have changed state before the session stopped. Inspect before retrying.` |

If a `tool_call_finished` exists for a started call that has no result, append ` It finished with exit status <exit_status>, but its result was lost.` to the reason. The status stays as the table says.

**Behavioral tests:**
- One test per table row, plus the finished-but-no-result variant for both a read-only and a mutating call (exact strings).
- A fully resolved log gives `[]`.
- Mixed: three calls in one step (resolved, started mutating, not started) give two actions, in log order.
- The side effect comes from `tool_call_started`: a call whose name would map to a different side effect in any registry still follows the logged value. The planner takes no registry at all, so this is structural, and the test asserts the signature takes only events.
- `repair_bodies` output appended to the log resolves every call: `unresolved_calls` on the result is `[]`, and the layers validate.
- Idempotence: planning on a log that already contains the repair bodies gives `[]`.

**Commit:** `feat(agent): three-state repair planner for dangling tool calls`

### Task 4: Loop core: steps, tool dispatch, steering, end conditions

**Files:** create `src/cookcode/agent/loop.py`, `tests/agent_helpers.py`, `tests/test_loop_steps.py`.

**Interfaces (produces):**
- `AgentConfig` (frozen) has:
  - `model: str`, `system_prompt: str`
  - `limits: Limits = Limits(max_turns=50)`
  - `tool_timeout_s: float = 120.0`, `max_tool_output_bytes: int = 30_000`
  - `max_parallel_tools: int = 8`, `cwd: str = "."`
- `RunOutcome(status: Literal["done", "error", "budget_exceeded", "interrupted"], turns: int, usage: Usage, last_seq: int)`: frozen.
- `Agent` has:
  - Constructor: `Agent(*, log: SessionLog, provider: Provider, env: Environment, tools: ToolRegistry, config: AgentConfig, harness_version: str = cookcode.__version__, repair_planner: Callable[[Sequence[Event]], list[RepairAction]] = plan_repairs)`.
  - `steer(text: str) -> None`: queues text. It is safe to call at any time, including while a run is active or before it.
  - `async run(prompt: str | None = None, *, cancel: CancelToken | None = None) -> RunOutcome`.
  - `run()` while another `run()` is active raises `RuntimeError`.

**Run algorithm (Task 4 scope, without interrupts and budgets other than the turn cap):**
1. If the log is empty, append `SessionStarted.for_config(RunConfig(...))`. Its fields are:
   - `provider = provider.name`
   - `model`
   - `tools = registry.names()`
   - `system_prompt_sha256` = sha256 hex of the system prompt
   - `harness_version`
   - `limits`
2. Run the repair planner over the log. Append the bodies from `repair_bodies` (Task 5 tests this. In Task 4 the log is always clean).
3. If `prompt` is given, append `UserMessage(prompt)`.
4. Loop over steps:
   1. Drain the steering queue into `SteerMessage` events.
   2. Check the turn cap: if `turns == max_turns`, append `BudgetExceeded(limit="turns", value=turns)` and finish with `budget_exceeded`.
   3. Build the request with a fresh `request_id = new_id()`, and append `ModelRequestStarted(request_id, view="raw", token_estimate)`.
   4. Stream. Append each `ItemDone.item` as `ItemEvent(item, request_id)` as it arrives. Ignore deltas. Remember the `UsageReport`.
   5. Append `ModelRequestFinished(request_id, stop_reason, usage)`.
   6. If the stop reason is `error`, or the stream raised: close out any logged calls of this response as not executed (results only), append `ErrorEvent(kind="provider", retryable=False, message)` and finish with `error`.
   7. Dispatch this response's `ToolCall` items per architecture call 4. For each call:
      - An unknown tool or invalid args (pydantic validation of `call.arguments`) gives an error `ToolResult` with a message naming the problem.
      - Otherwise:
        1. Append `ToolCallStarted(call_id=call.id, tool, arguments, side_effect)`.
        2. Run the handler with a `ToolContext` built from the config and the internal cancel token.
        3. Append `ToolCallFinished(call_id, exit_status, duration_s, output_bytes=size, truncated)`.
        4. Append `ItemEvent(ToolResult(call_id, status, content))`.
      - Status is `output.status` unless `exit_status == "killed"` (Task 5).
      - A handler exception gives `exit_status="error"`, status `error`, and content `tool raised <ExcType>: <message>`.
   8. If the response had tool calls, or the steering queue is non-empty, continue. Otherwise, finish with `done`.
5. To finish: append `SessionFinished(status, turns, usage)` and return `RunOutcome`. `usage` is the sum of this run's `UsageReport`s.

**Test helpers (`tests/agent_helpers.py`):**
- `kinds(events)` returns the list of `body.type`.
- `assert_every_call_resolved(events)` checks that `unresolved_calls` is empty and that each call has exactly one `ToolResult`.
- Test tools, all honoring cancel:
  - `echo` (read_only): returns its `text` arg.
  - `append` (mutating): appends a line to a file through `env.exec`.
  - `gate` (read_only): waits on a shared `asyncio.Barrier` with a short timeout. It returns ok if its peers arrive, and an error result on timeout, so it only succeeds when its peers run concurrently.
  - `wait_cancel` (configurable side effect): waits on `ctx.cancel.wait()` and returns `killed`.
  - `boom`: raises `RuntimeError("boom")`.

**Behavioral tests:**
- **Event order, one tool call.** A new session with `run("hi")` produces exactly this order, and the outcome is `done` with `turns == 2`:
  1. `session_started`
  2. `user_message`
  3. `model_request_started`
  4. `item` (ToolCall)
  5. `model_request_finished` (tool_use)
  6. `tool_call_started`
  7. `tool_call_finished`
  8. `item` (ToolResult ok)
  9. `model_request_started`
  10. `item` (Message)
  11. `model_request_finished` (end_turn)
  12. `session_finished` (done)
- **Second run.** A second `run("again")` on the same log does not write a second `session_started`, and ends with its own `session_finished`.
- **The model sees results.** The second recorded request in `FakeProvider.requests` contains the ToolCall followed by its ToolResult.
- **Read-only calls run concurrently.** Two `gate` calls in one response (barrier of 2) both finish ok. With `max_parallel_tools=1` they time out on the barrier and return error results. This proves the cap.
- **Mutating calls are ordered.** For a response of read, append, read, the timeline (recorded by the tools) shows that the append starts after the first read ends and the second read starts after the append ends.
- **Completion order versus call order.** Two read-only calls where the first is slower are logged as result 2 and then result 1, and the next request carries them as 1 and then 2.
- **Calls that never execute.** An unknown tool and invalid args (missing a required field) each produce an error result, with no `tool_call_started` for that call. A sibling valid call in the same response still runs.
- **A handler exception** gives `tool_call_finished(exit_status="error")` and an error result whose content contains `tool raised RuntimeError: boom`. The run continues to the next request.
- **Steering.**
  - Text steered before `run()` is logged after the `user_message` and before the first `model_request_started`.
  - Text steered from inside a tool handler during step 1 is logged after step 1's last result and before step 2's request.
  - Text steered while the final `end_turn` response is streaming (use `FakeProvider(event_delay_s=...)` and a concurrent task that steers once the request has started) causes one more request instead of finishing.
- **Turn cap.** With `max_turns=1` and a model that always calls a tool, the run ends `budget_exceeded`, with a `budget_exceeded(limit="turns")` event and the first step's tool result logged before it.
- **Provider error.** A `FakeTurn(fail_with="overloaded")` gives `error` and `session_finished(error)`. Script exhaustion (`FakeScriptExhausted` raised by the stream) gives the same.
- **Reentrancy.** Calling `run()` while a run is active raises `RuntimeError`.
- **Every log** produced in this file passes `assert_every_call_resolved`.

**Commit:** `feat(agent): step loop with write-ahead tool dispatch, concurrency policy and steering`

### Task 5: Interrupts, budgets and resume

**Files:** modify `src/cookcode/agent/loop.py`. Create `tests/test_loop_interrupts.py`, `tests/test_loop_resume.py`.

**Behavior to add:**
- **Layered cancel** (architecture call 9). The caller's token and the wall-clock watchdog (when `max_wall_s` is set) cancel an internal token, and only the internal token reaches providers and tools. Both watcher tasks are cleaned up on every exit path, including exceptions.
- **Close-out on graceful cancel.** Cancellation can land in one of three places. Each has its own phase and close-out:

  | Where it lands | Phase | Close-out |
  |---|---|---|
  | Before a request (idle) | `idle` | Nothing to close |
  | During streaming (stop reason `aborted`) | `streaming` | Every logged ToolCall of the response gets `ToolResult(interrupted, "not executed: ...")` (reuse the Task 3 not-started reason) |
  | During tools | `tool` | See below |

  Close-out for the `tool` phase:
  - A handler that returned `exit_status="killed"` gets `tool_call_finished(killed)` and a result whose status is `interrupted` for read-only calls or `unknown` for mutating/external ones. The content is the handler's partial output plus a one-line note saying the call was killed by an interrupt.
  - Calls that had not started get the not-started result.
  - A batch already running finishes its close-out before the loop exits.
  - `Interrupted.killed` lists the call ids that were running when the cancel landed.
- **Ending a cancelled run.**
  - Reason `wall_clock`: append `BudgetExceeded(limit="wall_clock", value=elapsed)` and finish with `budget_exceeded`.
  - Any other reason: append `Interrupted(phase, killed)` and finish with `interrupted`.
  - In both cases the close-out results come first.
- **Token budget.** At each step boundary, if this run's `usage.total_input + usage.output >= max_tokens`, append `BudgetExceeded(limit="tokens", value=...)` and finish with `budget_exceeded`.
- **Cost limit.** It is rejected in `__init__` (architecture call 11).
- **Resume.** Step 2 of the run algorithm becomes real. Repair bodies are appended before any `user_message` of this run. A crash or hard cancel leaves the log for repair (architecture call 10).

**Behavioral tests (interrupts):**
- **Pre-cancelled token.** No request is made (`FakeProvider.requests` is empty), the log has `interrupted(phase="idle")`, and the outcome is `interrupted`.
- **Cancel mid-stream.** Use `event_delay_s` and cancel after the first `ItemDone`. The finished items stay, the unfinished item is absent, logged ToolCalls get not-executed results, the log has `interrupted(phase="streaming")`, and every call is resolved.
- **Cancel during a mutating `wait_cancel`** gives:
  - `tool_call_started`, then `tool_call_finished(killed)`, then a result with status `unknown`
  - `interrupted(phase="tool", killed=(call_id,))`
  - outcome `interrupted`
- **Cancel during a read-only `wait_cancel`** gives the same, with status `interrupted`.
- **A mixed batch** (read-only `wait_cancel`, then a mutating `append` that never started) gets one killed result and one not-executed result. The `append` side effect never happened (the file is absent).
- **Wall clock.** With `max_wall_s=0.2` and a `wait_cancel` tool, the outcome is `budget_exceeded`, the log has `budget_exceeded(limit="wall_clock")`, and there is no `interrupted` event.
- **Token budget.** With `max_tokens` below the first request's usage, the run stops before the second request.
- **Cost limit.** Setting `max_cost_usd` raises `ValueError` at construction.
- **No leaks.** After every test in this file, no watcher tasks remain (`asyncio.all_tasks()` holds only the test task) and every call is resolved.

**Behavioral tests (resume):**
- **One dangling call per state.** Build a log by appending events directly: one dangling call per repair-table state, each the only dangling call in its own session. A new `Agent` on the reopened log, with `run(None)` and a script that ends the turn, gives:
  - a `repaired` event followed by a result with the exact Task 3 status and reason
  - then a request whose items include the repaired result
  - then `done`
- **Repair comes before the new prompt.** `run("continue")` on a dangling log appends the repair bodies before the new `user_message`.
- **Idempotence.** A second `run` on the repaired log adds no `repaired` events.
- **Hard cancel.** Start `run()` with a mutating `wait_cancel` tool and call `task.cancel()` on the run task once the tool has started. `CancelledError` propagates, and the log ends at `tool_call_started` for that call. Close the log, reopen it, and run again: the repair gives `unknown`.
- **Custom planner.** `repair_planner` can be swapped. A planner that returns `[]` leaves the dangling call, which the test detects with `unresolved_calls`. This is the seam the chaos baseline uses.

**Commit:** `feat(agent): graceful interrupts, budgets, and repair on resume`

### Task 6: Chaos scenario model

**Files:** create `src/cookcode/chaos/__init__.py`, `src/cookcode/chaos/scenario.py`, and the scenario tests in `tests/test_chaos.py`.

**Purpose:** a deterministic stand-in for a model that pursues a goal (append each of K unique lines to a file exactly once). It must keep working after any crash and repair. It is a `Provider` that decides from the request, not a fixed script.

**Interfaces (produces):**
- Tools via `chaos_tools(target: str, after_effect: Callable[[str], None] | None = None) -> ToolRegistry`:
  - `append_line(line: str)` is mutating. It runs `printf '%s\n' <shell-quoted line> >> <target>` through `ctx.env.exec`, then calls `after_effect(line)` if one was given. This is where the experiment injects a crash.
  - `read_target()` is read-only and returns the file content, or an empty string if the file is missing.
- `ScenarioProvider(lines: Sequence[str], per_step: int = 2)` is a `Provider` named `"scenario"`, with `capabilities()` returning the same caps as `FakeProvider`. Each request is decided by the policy below and streamed as `ItemDone` items, then `UsageReport` (fixed usage) and `StreamEnd`.
- `naive_plan_repairs(events) -> list[RepairAction]` is the baseline. Every unresolved call becomes `interrupted` with the not-executed reason, whatever its log state. This is what a harness without write-ahead intent can say.

**Policy, computed only from `request.items`:**
1. Map each `append_line` call to its line, and each result to its call.
2. A line is **confirmed** if:
   - any of its append calls has an `ok` result, or
   - a `read_target` result issued after its latest `unknown` result contains the line.
3. A line is **suspect** if its latest append result is `unknown` and no later `read_target` result exists.
4. If any line is suspect, respond with a single `read_target` call.
5. Otherwise, if any line is unconfirmed, respond with up to `per_step` append calls for the first unconfirmed lines, in order.
   - An unconfirmed line is one whose latest append result is `interrupted`, `error` or absent, or that a later read showed missing.
6. Otherwise, respond with the message `done` and `end_turn`.

**Behavioral tests:**
- A fresh run with 3 lines and `per_step=2` takes three requests (two appends, then one, then `done`), and the file has each line exactly once.
- Policy unit tests on hand-built request items:
  - an `unknown` result leads to a `read_target` call
  - a read that contains the line confirms it
  - a read that lacks the line leads to a re-append
  - an `interrupted` result leads to a re-append without a read
- `naive_plan_repairs` marks a started mutating call as `interrupted` (where `plan_repairs` says `unknown`).
- Tool call ids in the scenario are unique across requests.

### Task 7: Chaos experiment

**Files:** create `src/cookcode/chaos/worker.py` and `src/cookcode/chaos/experiment.py`, add experiment tests to `tests/test_chaos.py`, and generate `docs/experiments/chaos-m1.md`.

**Design:**
- **Reference run.** Run in-process, with lines `L1`, `L2`, `L3` and `per_step=2`. Wrap the log with a counting wrapper (a `SessionLog` that delegates) to get the total event count `E` and the number of side effects `S`.
- **Crash points.** There are two kinds:
  - `after_event:k` for every `k` in `0..E-1`: the process SIGKILLs itself right after `append` returns for seq `k`.
  - `after_effect:i` for every `i` in `1..S`: SIGKILL inside `append_line`, right after the exec that performed side effect `i`.
- **Crash run.** `python -m cookcode.chaos.worker --root <dir> --point <point>` runs the scenario in a subprocess with a `CrashingLog` wrapper or the `after_effect` hook. The driver asserts that the worker died by SIGKILL (returncode `-9`). A worker that finishes without crashing is a driver bug and fails loudly.
- **Two resumes from an identical state.** Copy the crashed directory (session store plus work dir) into `ours/` and `naive/`. In each copy, resume in-process with `Agent(..., repair_planner=plan_repairs)` or `naive_plan_repairs`, a fresh `ScenarioProvider` with the same lines, and one `run(None)`. A resume that ends with dangling calls or a status other than `done` counts as a resume failure.
- **Metrics per point and mode:**
  - `duplicates`: the sum over lines of `max(0, count - 1)` in the target file
  - `missing`: the number of lines with count 0
  - `resume_ok`: outcome `done`, `assert_every_call_resolved` passes, and seqs are contiguous from 0
  - `extra_requests`: the number of model requests in the resume
- **Report.** `python -m cookcode.chaos.experiment --out docs/experiments` writes `chaos-m1.md` and `chaos-m1.json`. The report contains:
  - the harness commit, the scenario parameters and the date
  - a per-point table
  - totals per mode
  - one paragraph stating the result in numbers
- **Honest caveat.** SIGKILL does not drop the page cache, so this experiment does not test fsync against power loss. The report states this.

**Behavioral tests (kept fast: run the subprocess path for a handful of points, and the full enumeration only in the experiment command):**
- `after_event` for the seq of the first `tool_call_started`: the worker dies with -9, and the log ends at that event.
- `after_effect:1`: the file has `L1` once and the log has `tool_call_started` with no `tool_call_finished`.
- At the `after_effect:1` point, `ours` has `duplicates == 0` and `missing == 0`, `naive` has `duplicates == 1`, and both have `resume_ok`.
- At the `after_event` point for the first `tool_call_started`, both modes have `duplicates == 0` and `missing == 0`. The effect never ran, so the extra verify step in `ours` costs one request and nothing else.
- The report generator writes both files, and the totals equal the sum of the rows.

**Run the full experiment** and commit the generated report.
- Expected shape: `ours` has 0 duplicates and 0 missing at every point.
- `naive` has duplicates exactly at the points between a side effect and its result.
- If the numbers differ from that shape, stop and report. Don't tune the scenario to fit.
